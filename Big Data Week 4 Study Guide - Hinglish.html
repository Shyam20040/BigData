2Writes, Reads & Storage

Write path

  • Writes lock-free aur fast hone chahiye (no reads ya disk seeks). Client ek coordinator ko send karta hai (per-key, per-client ya per-query; per-key writes serialize karta hai).
  • Coordinator Partitioner se sabhi replicas ko send karta hai; X replicas respond karne ke baad client ko acknowledge karta hai.
  • Hinted handoff (always writable): replica down ho toh coordinator baaki replicas par write karta hai aur replica ke return hone tak write locally rakhta hai; sabhi down hon toh writes buffer karta hai (kuch ghanton tak).
  • Har DC ke liye ek ring hoti hai; har DC ka coordinator other DCs ke saath coordinate karne ke liye elect hota hai via ZooKeeper (Paxos ka ek variant).
1 Commit log disk par, recovery ke liye
→
2 Memtable in-memory, append-only, write-back cache jo key se searchable hai
→
3 Flush full/old ho toh → SSTable data file + index file + Bloom filter

SSTable = Sorted String Table, key-value pairs key ke according sorted hote hain; immutable. Index file = SSTable of (key, position in data file).

Bloom filterCompact set representation hai; cheap membership check deta hai; false positives possible, never false negatives. Insert par saare hashed bits set hote hain; check true tabhi return karta hai jab saare hashed bits set hon. Example: 4 hash functions, 100 items, 3200 bits → false-positive rate 0.02%.
  • Compaction: periodically, har server par locally, SSTables merge karta hai (kisi key ke updates merge karte hue).
  • Deletes: ek tombstone add hota hai; compaction mein milne par item remove hota hai.
  • Reads: coordinator X replicas se contact karta hai (quickest responders), latest-timestamped value return karta hai; background mein other replicas bhi check karta hai aur values alag hon toh read repair start karta hai. Ek row multiple SSTables mein ho sakti hai, isliye reads writes se slower hain (phir bhi fast).

3Membership & Failure Detection

Koi bhi server coordinator ho sakta hai, isliye har server all servers ki list rakhta hai jo automatically update hoti hai. Cassandra gossip-style membership use karta hai: nodes periodically apni lists gossip karte hain (address, local time, heartbeat counter); receivers latest heartbeat rakhte hain; heartbeat isse purana ho toh Tfail node ko failed mark kiya jaata hai.

Suspicion (accrual detector)Failure detector PHI suspicion value output karta hai. Gossip messages ke inter-arrival times se network behavior ke mutabik timeout adapt hota hai; applications threshold set karti hain. PHI(t) = −log(P(tnow − tlast)) / log 10. Practice mein PHI = 5 → 10–15 s detection.

4CAP Theorem

Eric Brewer ne propose kiya, Gilbert aur Lynch ne prove kiya: distributed system 3 mein se maximum 2 properties satisfy kar sakta hai:

Consistency – sabhi nodes same data dekhte hain; reads latest write return karte hain. (E.g. devices ke across bank accounts, flight booking.)
Availability – operations hamesha allowed aur fast hote hain. (500 ms extra latency → 20% revenue drop; Amazon mein each ms ≈ $6M/year; SLAs latency ke around hote hain.)
Partition-tolerance – network partitions ke bawajood work karta hai (router outages, cut cables, DNS failure, rack switch outage).

Cloud systems mein partition-tolerance essential hai, isliye consistency aur availability mein se ek choose karna padta hai.

Pair chosenSystems
C + PHBase, HyperTable, BigTable, Spanner
C + ANon-replicated RDBMSs
A + PCassandra, Riak, Dynamo, Voldemort

Cassandra vs MySQL (>50 GB): MySQL writes 300 ms, reads 350 ms; Cassandra writes 0.12 ms, reads 15 ms – iska cost strong consistency hai. ACID (RDBMS: Atomicity, Consistency, Isolation, Durability) vs BASE (key-value stores: Basically Available, Soft-state, Eventual consistency – availability ko prefer karta hai).

Eventual consistencyAgar kisi key par writes ruk jaati hain toh sab replicas eventually converge karte hain. Writes continue hon toh updates ki "wave" lag karti hai, par catch up karti rehti hai; stale values return ho sakti hain. Low-write periods mein achha work karta hai.

5Quorums & Consistency Levels

Quorum = majority (>50%); koi bhi two quorums intersect karte hain, isliye read quorum mein latest write wala kam se kam ek server hota hai. ALL se faster, phir bhi strongly consistent. Reads: client R set karta hai (≤ N replicas); coordinator R ka wait karta hai aur remaining N−R ko background mein repair karta hai. Writes: client W set karta hai; coordinator quorum tak block karta hai ya asynchronously write karta hai.

Necessary conditionsW + R > N and W > N/2.
(W=1,R=1): few reads/writes · (W=N,R=1): read-heavy · (W=N/2+1,R=N/2+1): write-heavy · (W=1,R=N): mostly ek writer per key ke saath write-heavy.
LevelMeaning
ANYKoi bhi server (replica hona zaroori nahi); fastest – coordinator write cache karta hai.
ALLSabhi replicas; strong consistency, slowest.
ONEKam se kam ek replica; ALL se faster, failures na hon toh durability ensure hoti hai.
QUORUMSabhi DCs ke replicas mein quorum; global consistency, phir bhi fast.
LOCAL_QUORUMSirf coordinator ke DC mein quorum; faster.
EACH_QUORUMHar DC mein quorum; hierarchical replies support karta hai.

6Consistency Models Spectrum

Left (faster reads/writes) se right (more consistency) tak: Eventual → Per-key sequential → Causal → Red-Blue / CRDTs / Probabilistic → Strong (e.g. sequential). Rule: application ke liye jo model correct ho, usmein lowest (leftmost) model use karo.

ModelIdea
EventualWrites rukne par replicas converge karte hain; Amazon Dynamo aur LinkedIn Voldemort mein use hua.
Per-key sequentialHar key ke liye sab operations ka global order hota hai.
CRDTsCommutative Replicated Data Types: commuted writes same result deti hain (e.g. integer jisme sirf +1 ho), isliye servers ko consistency ki chinta nahi karni padti.
Red-BlueBlue operations DCs ke across kisi bhi order mein run ho sakti hain; red operations har DC par same order mein run honi chahiye.
CausalReads information flow ke partial order ko respect karte hain. E.g. A: W(K1,33); B 33 read karke W(K2,55) karta hai; C agar K2=55 read kare toh K1=33 bhi read karna hoga.
LinearizabilityHar operation real time mein all clients ko instantaneously visible hoti hai.
Sequential (Lamport)Result all operations ke kisi sequential order ke barabar hota hai, jo har processor ka program order respect karta hai.

"NewSQL" = NoSQL + ACID transactions (e.g. HyperDex, Spanner, transaction chains).

7CQL (Cassandra Query Language)

Cassandra ek distributed columnar store hai: no SPOF, tunably consistent, write-optimized aur scalable. Iske challenges (no joins/schema, huge tables) ko CQL solve karta hai: schema ko re-introduce karta hai, common data-modeling language aur best-practice SQL-like interface deta hai. CQL protocol binary (language-interoperable), asynchronous (Thrift synchronous hai) hai aur prepared statements allow karta hai.

Data model: Keyspace (database) → Column Family (table) → rows (row key) → columns (name, value or tombstone, timestamp, time-to-live). Rows mein koi bhi number of columns ho sakte hain; values omit ho sakti hain; row key ka partitioner aur column name ka comparator hota hai.

Write pathInsert memtable + commit log mein hota hai; write se pehle read nahi; isliye bahut fast.
Read pathMemtable → row cache → Bloom filter se SSTables dhoondhna → key cache → SSTables → row cache repopulate karna.

Remember: Cassandra rows ko fast find karta hai, columns ko fast scan karta hai, rows scan nahi karta.

CREATE TABLE users (id timeuuid PRIMARY KEY, lastname varchar,
                    firstname varchar, dateOfBirth timestamp);
INSERT INTO users (id, lastname, firstname, dateofbirth)
  VALUES (now(), 'Berryman','John','1975-09-15');
SELECT dateofbirth, firstname, lastname FROM users;
CQL primary keyInternal mapping
PRIMARY KEY (name)name = row key (partition); har doosra CQL column = ek Cassandra column.
PRIMARY KEY (company, name)company = row key; compound column names: e.g. OSC row: eric:age 38, eric:role ceo, john:age 37…
PRIMARY KEY ((A,B),C,D)(A,B) composite row key; clustering columns C,D column names ke prefixes hote hain, e.g. c:d:E, c:d:F.

Collections: set (unique elements), list (ordered, repeats allowed), map (key-value pairs); primary key ka part nahi ban sakte. Extra columns ke form mein stored hote hain: set element column name mein (b:myset:1), list time-UUID name use karti hai, map key column name mein hoti hai (b:mymap:m). Update syntax: myset = myset + {'apple'}, mylist = ['x'] + mylist, mymap['fruit'] = 'apple'.

8ZooKeeper: Why & What

Classic system: ek master aur kai slaves (e.g. HDFS). Fault-tolerant system mein backup master aur coordination service add ki jaati hai.

Race conditionDo processes compete karte hain aur data corrupt ho jaata hai: account mein 17 Rs hain aur do log 1 Rs deposit karte hain; dono 17 read karke 18 write kar dete hain, 19 nahi.
DeadlockProcesses directly ya indirectly ek-doosre ka wait karte hain (P1→P2→P3→P1) aur kabhi khatam nahi hote.

Coordination needs: group membership, leader election, dynamic configuration (service registry), status monitoring, queuing, barriers, critical sections. Example: alag machines par email-indexer processes ko ek central, concurrency-safe store chahiye taaki same email multiple times index na ho – ZooKeeper yeh kaam karta hai.

DefinitionZooKeeper ek highly reliable distributed coordination kernel aur distributed applications ke liye metadata hold karne wali replicated service hai (small, performance-sensitive, dynamic, critical). Yeh coordination ke liye central key-value store jaisa hai, jo khud multiple machines par run karta hai. Uses: locking, synchronization, configuration, leader election, work queues – race conditions aur deadlocks se bachane ke liye.

Design goals

Simple – file system jaisa shared hierarchical namespace of znodes; data memory mein hota hai → high throughput, low latency.
Replicated – servers ka ensemble, har server ke paas in-memory state; startup par leader elect hota hai; followers clients ko serve karte hain, sab updates leader ke through jaate hain; majority persist hone ke baad reply milta hai; 2f+1 machines, f failures tolerate kar sakti hain.
Ordered – har update ko ek number milta hai jo transaction order dikhata hai (synchronization primitives ka basis).
Fast – read-heavy loads (~10:1) ke liye best; Yahoo! benchmark mein >10,000 write-dominant ops/s.

Clients TCP connection maintain karte hain, watch events receive karte hain, heartbeats bhejte hain, aur connection tootne par doosre server se reconnect karte hain. Servers in-memory state ke saath persistent transaction logs aur snapshots rakhte hain.

Data model

Highly available file system ki tarah: data znodes mein stored hota hai (JSON data; poora update hota hai – append nahi); reads/writes atomic hote hain; znodes ke children ho sakte hain, jisse "/" se rooted tree banta hai (e.g. /zoo/duck); "." aur ".." invalid hain.

Znode typeBehavior
PersistentDefault; delete na hone tak rehta hai (create /name "data").
EphemeralCreating session end hone par delete ho jaata hai (tab tak doosron ko visible); children nahi ho sakte.
Sequentialcreate -s name ke end mein monotonically increasing counter append karta hai (e.g. /zoo0000000008); har parent apna counter rakhta hai.

9ZooKeeper Architecture

Modes: Standalone (ek machine; sirf testing ke liye; HA nahi) aur Replicated (ensemble; highly available; majority survive hone tak failures tolerate karta hai).

Phase 1: Leader electionPaxos-like; majority leader ke saath sync ho jaaye toh complete; re-election ~200 ms; majority lose hone par leader step down karta hai
→
Phase 2: Atomic broadcastWrites leader ko forward → broadcast → majority persist → leader commit → client ko success (two-phase commit jaisa; disk before memory)

Election details (Zab – ZooKeeper Atomic Broadcast)

  • Har server next-higher sequence ID leta hai (ZK file system ke through); highest ID leader banta hai.
  • Naïve failure handling (sab leader ko monitor karte hain) election flood create karti hai. ZooKeeper ka tareeqa: har process apne next-higher-ID process ko monitor karta hai; agar woh leader tha aur fail ho gaya, toh yeh leader banta hai; warna wait karke recheck karta hai.
  • ID conflicts / election ke beech leader failure: leader NEW_LEADER bhejta hai; har process maximum ek leader ko ACK karta hai (highest ID); majority ACK milne par leader COMMIT bhejta hai; processes apna leader variable update karte hain – safety bani rehti hai.
Majority kyun?3 nodes mein leader die ho jaaye → bache hue 2 (majority) leader elect karte hain. 3 mein se 2 die ho jaayein → leader nahi (1/3 majority nahi). 6-server ensemble ko two data centres mein split karne par majority rule ke bina dono sides apna leader elect kar sakti hain → inconsistency aur chaos.

Sessions

Client apni list ke servers try karta hai jab tak connect na ho; server timeout ke saath session create karta hai. Timeout ke andar request na aaye toh session expire ho sakta hai aur ephemeral nodes lost ho jaate hain; client library pings (heartbeats) bhejti hai. Sessions server switch ke baad bhi survive karti hain; failover automatic hai, lekin disconnection ke dauran operations fail hote hain. States: CONNECTING → CONNECTED (SyncConnected) ⇄ Disconnected; Expired/close → CLOSED.

10ZooKeeper: Usage

Guarantees: sequential consistency (ek client ke updates order mein apply), atomicity, single system image (new server client ko tab tak accept nahi karega jab tak fully caught up na ho), durability, timeliness (bahut stale data nahi milta).

OperationPurpose
createZnode create karna (parent ka exist karna zaroori hai)
deleteZnode delete karna (children nahi hone chahiye)
existsExistence check karna, metadata lena
getACL / setACLAccess control list
getChildren (ls)Children ki list dekhna
getData (get) / setDataData read / write karna
syncClient view ko ZooKeeper ke saath sync karna

Multi-update multiple operations ko batch karta hai: ya sab succeed, ya sab fail, jisse transactions enable hote hain. APIs: Java aur C core mein hain; Perl, Python, REST contrib mein hain; synchronous aur asynchronous versions available hain.

Watch onTriggered when znode is…

Watches sirf ek baar fire hote hain (aur events ke liye re-register karna padta hai); read operations se set hote hain aur write operations (create, delete, setData) se trigger; ACL operations ismein participate nahi karte. ACL = authentication scheme + identity + permissions; schemes: digest (username/password), sasl (Kerberos), ip.

Server discovery use caseHar server /servers ke andar ek ephemeral znode create karta hai (e.g. duck, cow); clients ls /servers run karte hain. Duck die ho jaaye toh uska znode vanish ho jaata hai aur next ls sirf cow return karta hai.

Other uses: reliable configuration service, distributed lock service (sirf ek process lock hold karta hai). Applications: Yahoo! Fetching Service (crawler configuration metadata, master election), Katta (distributed indexer: group membership, failover, shard assignment), Yahoo! Message Broker (publish-subscribe: topic distribution, failure detection, membership; "nodes" ke andar ephemeral znodes, topic znodes with primary/backup).

When not to use: big data store karne ke liye (copies = nodes ki count, sab RAM mein, network load) aur jab extremely strong consistency required ho.

11Quick Revision

Must remember
  • Placement: SimpleStrategy (Random/ByteOrdered partitioner) vs NetworkTopologyStrategy; snitches IP → rack/DC map karte hain.
  • Write: commit log → memtable → SSTable (+ index + Bloom filter); compaction; tombstones; hinted handoff; read repair.
  • Gossip membership; PHI accrual detector (PHI 5 ≈ 10–15 s).
  • CAP: 2 choose karo; Cassandra = A+P (eventual, BASE); RDBMS = ACID.
  • Quorum: W+R > N aur W > N/2; levels ANY, ONE, QUORUM, LOCAL_QUORUM, EACH_QUORUM, ALL.
  • CQL: row key = partition; compound keys compound column names mein convert hote hain; collections primary keys mein nahi hote.
  • ZooKeeper: znodes (persistent, ephemeral, sequential); 2f+1 ensemble; leader election + atomic broadcast (Zab); majority rule; watches one-time fire hote hain.
