2Writes, Reads & Storage

Write path

Writes ko lock-free aur fast hona chahiye, yani write ke time reads ya disk seeks nahi hone chahiye.

Client ek coordinator ko send karta hai:

  • per-key
  • per-client
  • ya per-query

Per-key writes ko serialize karta hai.

Coordinator Partitioner ka use karke write ko saare replicas ko send karta hai. Jab X replicas respond kar dete hain, coordinator client ko acknowledgement de deta hai.

Hinted Handoff — Always Writable: Agar koi replica down hai:

  • Coordinator baaki replicas ko write karta hai.
  • Write ko locally keep karta hai.
  • Jab failed replica wapas aata hai, stored write usse forward kar di jaati hai.

Agar saare replicas down hain, to Cassandra writes ko buffer karta hai — generally few hours tak.

Har DC ke liye one ring hoti hai.

Ek per-DC coordinator elect hota hai jo other DCs ke saath ZooKeeper ke through coordinate karta hai; ye Paxos ka ek variant use karta hai.

Storage Path: Commit Log: Disk par store hota hai aur recovery ke liye use hota hai.

Bloom filter

Bloom filter ek compact set representation hai jo cheap membership check provide karta hai.

Important:

  • False positives possible
  • False negatives never possible

Insert ke time:

  • All hashed bits set kiye jaate hain.

Check ke time:

  • true tabhi return hota hai jab all hashed bits set hon.

Example

  • 4 hash functions
  • 100 items
  • 3200 bits
  • False-positive rate = 0.02%

Compaction: Periodically, har server par locally SSTables merge kiye jaate hain.

Agar kisi key ke multiple updates hain, compaction unhe merge karta hai.

Deletes: Delete ke liye ek tombstone add hota hai.

Actual item tab remove hota hai jab compaction us tombstone ko process karta hai.

Reads: Coordinator X replicas ko contact karta hai — generally quickest responders.

Phir:

  • Latest-timestamped value return karta hai.
  • Background mein other replicas ko bhi check karta hai.
  • Agar values different hain, to read repair start karta hai.

Ek row multiple SSTables mein spread ho sakti hai, isliye reads writes se slower hote hain, although still fast.

3Membership & Failure Detection

Cassandra mein koi bhi server coordinator ban sakta hai.

Isliye har server ke paas all servers ki list hoti hai aur ye list automatically update hoti rehti hai.

Cassandra gossip-style membership use karta hai.

Nodes periodically apni lists gossip karte hain, jisme:

  • Address
  • Local time
  • Heartbeat counter

hota hai.

Receivers latest heartbeat ko maintain karte hain.

Agar heartbeat Tfail se zyada old ho jaata hai, to node ko failed mark kar diya jaata hai.

Suspicion (accrual detector)

Failure detector ek PHI suspicion value output karta hai.

Ye network behavior ke according timeout adapt karta hai, gossip messages ke inter-arrival times ka use karke.

Formula:

PHI(t) = −log(P(tnow − tlast)) / log 10

Practical case mein:

PHI = 5 → approximately 10–15 s detection

4CAP Theorem

CAP Theorem Eric Brewer ne propose kiya tha aur Gilbert aur Lynch ne prove kiya.

Ek distributed system maximum 3 mein se 2 properties satisfy kar sakta hai:

C — Consistency: Sabhi nodes ko same data dikhega aur reads latest write return karengi.

Examples:

  • Bank accounts across devices
  • Flight booking

A — Availability: Operations always allowed aur fast honi chahiye.

Example:

  • 500 ms extra latency → approximately 20% revenue drop
  • Amazon par each additional ms ≈ $6M/year
  • SLAs mainly latency ke around hote hain.

P — Partition Tolerance: Network partition ke despite system work karta rahe.

Examples:

  • Router outages
  • Cut cables
  • DNS failure
  • Rack switch outage

Cloud systems mein partition tolerance essential hai, isliye practically choice Consistency vs Availability ke beech hoti hai.

Pair ChosenSystems

Cassandra ki speed ka cost strong consistency hai.

ACID vs BASE: RDBMS → ACID

  • Atomicity
  • Consistency
  • Isolation
  • Durability

Key-value stores → BASE

  • Basically Available
  • Soft-state
  • Eventual consistency

BASE approach availability ko prefer karta hai.

Eventual consistency

Agar kisi key par writes stop ho jaati hain, to eventually all replicas converge kar jaate hain.

Jab writes continuously ho rahi hoti hain:

  • Updates ki ek "wave" lag karti hai.
  • Lekin continuously catch up karti rehti hai.
  • Is period mein stale values return ho sakti hain.

Ye model un situations mein achha work karta hai jahan low-write periods hote hain.

5Quorums & Consistency Levels

Quorum: Quorum = majority (>50%)

Kisi bhi do quorums ka intersection hota hai, isliye read quorum mein at least ek server aisa hota hai jiske paas latest write hoti hai.

Quorum:

  • ALL se faster hota hai.
  • Strong consistency provide kar sakta hai.

Reads: Client R set karta hai:

R ≤ N replicas

Coordinator R replicas ka response wait karta hai aur remaining:

N − R

replicas ko background mein repair karta hai.

Writes: Client W set karta hai.

Coordinator:

  • Quorum tak block kar sakta hai
  • Ya writes asynchronously kar sakta hai.
Necessary conditions

Strong consistency ke liye:

W + R > N

and

W > N/2

Common Configurations

  • (W=1, R=1) → few reads/writes
  • (W=N, R=1) → read-heavy
  • (W=N/2+1, R=N/2+1) → write-heavy
  • (W=1, R=N) → write-heavy with mostly one writer per key

Consistency Levels

LevelMeaning
ANYAny server, replica hona zaroori nahi; fastest. Coordinator write ko cache karta hai.
ALLAll replicas; strong consistency, but slowest.
ONEAt least one replica; ALL se faster, aur failures ke absence mein durability ensure karta hai.
QUORUMAll DCs ke across quorum; global consistency aur still fast.
LOCAL_QUORUMSirf coordinator ke DC mein quorum; faster.
EACH_QUORUMHar DC mein quorum; hierarchical replies support karta hai.

7CQL (Cassandra Query Language)

Cassandra ek:

  • Distributed columnar store
  • No SPOF
  • Tunably consistent
  • Write-optimized
  • Scalable

system hai.

Cassandra Challenges: Cassandra mein:

  • No joins
  • No traditional schema
  • Huge tables

jaise challenges hain.

CQL in challenges ko address karta hai by providing:

  • Schema ka re-introduction
  • Common data-modeling language
  • Best-practice SQL-like interface

CQL Protocol: CQL protocol:

  • Binary hai → language-interoperable
  • Asynchronous hai → Thrift synchronous tha
  • Prepared statements allow karta hai

CQL Data Model: Hierarchy:

Keyspace (database) ↓ Column Family (table) ↓ Rows (row key) ↓ Columns

Column ke components:

  • Name
  • Value or tombstone
  • Timestamp
  • Time-to-live

Rows mein any number of columns ho sakte hain.

Values omit bhi kiye ja sakte hain.

  • Row key → Partitioner
  • Column name → Comparator

Write Path: Insert hota hai:

Memtable + Commit Log

Write se pehle read ki requirement nahi hoti, isliye write very fast hota hai.

8ZooKeeper: Why & What

Classic System: Classic distributed system mein:

One Master + Many Slaves

Example:

HDFS

Fault-tolerant system mein ek backup master aur ek coordination service add ki jaati hai.

Race Condition: Do processes same data ko simultaneously modify karne ki koshish karte hain aur data corrupt ho sakta hai.

Example:

Account mein 17 Rs hain.

Do people simultaneously 1 Rs deposit karte hain.

Dono:

17 read

karte hain aur:

18 write

kar dete hain.

Expected result:

19

But actual result:

18

Deadlock: Processes ek doosre ka wait karte rehte hain, directly ya indirectly.

Example:

P1
P2
P3
P1

Aur process kabhi finish nahi hota.

Coordination Needs: Distributed applications ko coordination ke liye:

  • Group membership
  • Leader election
  • Dynamic configuration
  • Service registry
  • Status monitoring
  • Queuing
  • Barriers
  • Critical sections

ki need hoti hai.

Example: Different machines par multiple email-indexer processes run kar rahe hain.

Unhe ek central, concurrency-safe store chahiye taaki same email ko multiple processes index na karein.

Yahi role ZooKeeper play karta hai.

Definition

ZooKeeper ek highly reliable distributed coordination kernel aur replicated service hai jo distributed applications ka metadata hold karta hai.

Ye applications generally:

  • Small
  • Performance-sensitive
  • Dynamic
  • Critical

hoti hain.

ZooKeeper ko coordination ke liye ek central key-value store ki tarah samajh sakte hain, jo khud multiple machines par run karta hai.

Uses

  • Locking
  • Synchronization
  • Configuration
  • Leader election
  • Work queues

Aur ye race conditions aur deadlocks se protection provide karta hai.

Design goals

Simple: Shared hierarchical namespace provide karta hai, jo file system jaisa hota hai.

Is namespace ke objects ko znodes kehte hain.

Data memory mein hota hai, isliye:

  • High throughput
  • Low latency

milti hai.

Replicated: ZooKeeper ek ensemble of servers hota hai.

Har server ke paas in-memory state hoti hai.

  • Startup par leader elected hota hai.
  • Followers clients ko serve karte hain.
  • All updates leader ke through jaate hain.
  • Majority ke persist hone ke baad reply diya jaata hai.

2f + 1 machines → f failures tolerate kar sakti hain.

Ordered: Har update ko ek number ke saath stamp kiya jaata hai jo transaction order represent karta hai.

Ye synchronization primitives ka basis hai.

Fast: Read-heavy workloads ke liye best:

~10:1 read/write ratio

Yahoo! benchmark:

>10,000 write-dominant operations/sec

Clients & Servers: Clients TCP connection maintain karte hain, watch events receive karte hain aur heartbeats send karte hain.

Agar connected server break ho jaata hai, client automatically kisi doosre server se reconnect kar sakta hai.

Servers maintain karte hain:

  • In-memory state
  • Persistent transaction logs
  • Snapshots

Data model

ZooKeeper ek highly available file system jaisa hai.

Data znodes mein stored hota hai.

  • JSON data
  • Whole update hota hai
  • Append operation nahi hota
  • Reads/writes atomic hote hain

Znodes ke children ho sakte hain, jisse ek tree structure banta hai.

9ZooKeeper Architecture

ZooKeeper ke two modes hain:

Standalone

  • One machine
  • Testing ke liye
  • No High Availability

Replicated

  • Ensemble
  • Highly available
  • Jab tak majority survive karti hai, failures tolerate karta hai.

Phase 1: Leader Election: Leader election Paxos-like hai.

Leader election tab complete hoti hai jab majority leader ke saath sync kar leti hai.

Re-election approximately:

~200 ms

Agar leader majority lose kar deta hai, to leader step down karta hai.

Phase 2: Atomic Broadcast: Flow:

Writes forwarded to Leader

↓

Broadcast

↓

Majority persist

↓

Leader commits

↓

Client gets success

Ye approximately two-phase commit jaisa hai.

Important:

Disk before memory

Election details (Zab – ZooKeeper Atomic Broadcast)

Zab = ZooKeeper Atomic Broadcast

Har server next-higher sequence ID leta hai, jo ZK file system ke through milti hai.

Highest ID → Leader

Naïve Failure Handling: Agar everyone leader ko monitor kare, to leader failure ke time election flood create ho sakta hai.

ZooKeeper ka approach:

Har process apne next-higher-ID process ko monitor karta hai.

  • Agar woh leader tha aur fail ho gaya → current process leader ban sakta hai.
  • Otherwise → wait karta hai aur recheck karta hai.

ID Conflicts / Leader Failure: Leader:

NEW_LEADER

send karta hai.

Har process maximum one leader ko ACK karta hai — highest ID wale leader ko.

Majority ACKs milne par:

COMMIT

send hota hai.

Phir processes apna leader variable update karte hain.

Isse safety preserve hoti hai.

Why majority?

Agar leader die ho jaata hai:

Remaining 2 = majority

→ new leader elect ho sakta hai.

3 Nodes: Agar 2 nodes die ho jaate hain:

Remaining 1/3

→ majority nahi hai.

→ No leader.

6-server ensemble across 2 DCs: Agar majority rule na ho, to dono data centers apna-apna leader elect kar sakte hain.

Result:

Inconsistency + Chaos

Isliye majority rule essential hai.

Sessions

Client apni server list se servers try karta hai jab tak connection establish na ho.

Connected server ek session with timeout create karta hai.

Agar timeout ke andar request nahi aati:

  • Session expire ho sakta hai.
  • Ephemeral nodes lost ho jaate hain.

Client library automatically pings / heartbeats send karti hai.

Sessions server switch karne ke baad bhi survive kar sakte hain.

Failover automatic hai, lekin disconnection ke time operations fail ho sakte hain.

States: CONNECTING → CONNECTED (SyncConnected) ⇄ Disconnected

Then:

Expired / close → CLOSED
