1Cassandra: Data Placement

Replication strategyDetails
SimpleStrategyUses the Partitioner: RandomPartitioner (Chord-like hash partitioning) or ByteOrderedPartitioner (assigns key ranges to servers; easier for range queries, e.g. twitter users starting with [a–b]).
NetworkTopologyStrategyFor multi-DC deployments; e.g. two or three replicas per DC. Per DC: first replica placed by the Partitioner, then go clockwise around the ring until a different rack is hit (rack-failure tolerance).

Snitches

A snitch maps IPs to racks and DCs; configured in cassandra.yaml. Options: SimpleSnitch (topology-unaware), RackInferring (infers topology from octets of the IP, e.g. 101.102.103.104), PropertyFileSnitch (config file), EC2Snitch (EC2 region = DC, availability zone = rack), and others.

2Writes, Reads & Storage

Write path

  • Writes must be lock-free and fast (no reads or disk seeks). Client sends to one coordinator (per-key, per-client or per-query; per-key serializes writes).
  • Coordinator uses the Partitioner to send to all replicas; after X replicas respond it acknowledges the client.
  • Hinted handoff (always writable): if a replica is down, the coordinator writes to the others and keeps the write locally until the replica returns; if all are down it buffers writes (up to a few hours).
  • One ring per DC; a per-DC coordinator is elected to coordinate with other DCs via ZooKeeper (a Paxos variant).

→
2 Memtablein-memory, append-only, write-back cache searchable by key

3 Flushwhen full/old → SSTable data file + index file + Bloom filter

SSTable = Sorted String Table, key-value pairs sorted by key; immutable. Index file = SSTable of (key, position in data file).

Bloom filterCompact set representation; cheap membership check; false positives possible, never false negatives. Insert sets all hashed bits; check returns true only if all hashed bits are set. Example: 4 hash functions, 100 items, 3200 bits → false-positive rate 0.02%.
  • Compaction: periodically, locally per server, merges SSTables (merging updates for a key).
  • Deletes: a tombstone is added; the item is removed when compaction meets it.
  • Reads: coordinator contacts X replicas (quickest responders), returns the latest-timestamped value; also checks other replicas in the background and starts read repair if values differ. A row may span multiple SSTables, so reads are slower than writes (still fast).

3Membership & Failure Detection

Any server can be coordinator, so each keeps a list of all servers, updated automatically. Cassandra uses gossip-style membership: nodes periodically gossip their lists (address, local time, heartbeat counter); receivers keep the latest heartbeat; a heartbeat older than Tfail marks the node failed.

Suspicion (accrual detector)The failure detector outputs PHI, a suspicion value, adapting the timeout to network behavior using inter-arrival times of gossip messages; applications set a threshold. PHI(t) = −log(P(tnow − tlast)) / log 10. In practice PHI = 5 → 10–15 s detection.

4CAP Theorem

Proposed by Eric Brewer, proved by Gilbert and Lynch: a distributed system can satisfy at most 2 of 3:

Consistency – all nodes see the same data; reads return the latest write. (Needed e.g. bank accounts across devices, flight booking.)
Availability – operations always allowed and fast. (500 ms extra latency → 20% revenue drop; at Amazon each ms ≈ $6M/year; SLAs are about latency.)
Partition-tolerance – works despite network partitions (router outages, cut cables, DNS failure, rack switch outage).

Since partition-tolerance is essential in cloud systems, one must choose between consistency and availability.

Pair chosenSystems
C + PHBase, HyperTable, BigTable, Spanner
C + ANon-replicated RDBMSs
A + PCassandra, Riak, Dynamo, Voldemort

Cassandra vs MySQL (>50 GB): MySQL writes 300 ms, reads 350 ms; Cassandra writes 0.12 ms, reads 15 ms – the cost is strong consistency. ACID (RDBMS: Atomicity, Consistency, Isolation, Durability) vs BASE (key-value stores: Basically Available, Soft-state, Eventual consistency – prefers availability).

Eventual consistencyIf writes to a key stop, all replicas converge. While writes continue, a "wave" of updates lags behind but keeps catching up; stale values may be returned. Works well when there are periods of low writes.

5Quorums & Consistency Levels

Quorum = majority (>50%); any two quorums intersect, so a read quorum contains at least one server with the latest write. Faster than ALL yet strongly consistent. Reads: client sets R (≤ N replicas); coordinator waits for R, and repairs the other N−R in background. Writes: client sets W; coordinator either blocks until quorum or writes asynchronously.

Necessary conditionsW + R > N and W > N/2.
(W=1,R=1): few reads/writes · (W=N,R=1): read-heavy · (W=N/2+1,R=N/2+1): write-heavy · (W=1,R=N): write-heavy with mostly one writer per key.
LevelMeaning
ANYAny server (may not be a replica); fastest – coordinator caches write.
ALLAll replicas; strong consistency, slowest.
ONEAt least one replica; faster than ALL, ensures durability without failures.
QUORUMQuorum across all replicas in all DCs; global consistency, still fast.
LOCAL_QUORUMQuorum in the coordinator's DC only; faster.
EACH_QUORUMQuorum in every DC; supports hierarchical replies.

6Consistency Models Spectrum

From left (faster reads/writes) to right (more consistency): Eventual → Per-key sequential → Causal → Red-Blue / CRDTs / Probabilistic → Strong (e.g. sequential). Rule: use the lowest (leftmost) model that is correct for your application.

ModelIdea
EventualReplicas converge if writes stop; from Amazon Dynamo and LinkedIn Voldemort.
Per-key sequentialPer key, all operations have a global order.
CRDTsCommutative Replicated Data Types: commuted writes give the same result (e.g. integer with only +1), so servers need not worry about consistency.
Red-BlueBlue operations may run in any order across DCs; red operations must run in the same order at every DC.
CausalReads respect partial order of information flow. E.g. A: W(K1,33); B reads 33 then W(K2,55); C reading K2=55 must read K1=33.
LinearizabilityEach operation visible instantaneously (real time) to all clients.
Sequential (Lamport)Result equals some sequential order of all operations that respects each processor's program order.

"NewSQL" = NoSQL + ACID transactions (e.g. HyperDex, Spanner, transaction chains).

7CQL (Cassandra Query Language)

Cassandra: distributed columnar store, no SPOF, tunably consistent, write-optimized, scalable. Its challenges (no joins/schema, huge tables) are solved by CQL: a re-introduction of schema, a common data-modeling language, a best-practice SQL-like interface. CQL protocol is binary (language-interoperable), asynchronous (Thrift is synchronous) and allows prepared statements.

Data model: Keyspace (database) → Column Family (table) → rows (row key) → columns (name, value or tombstone, timestamp, time-to-live). Rows may have any number of columns; values can be omitted; row key has a partitioner, column name a comparator.

Write pathInsert into memtable + commit log; no read before write; very fast.
Read pathMemtable → row cache → Bloom filter to find SSTables → key cache → SSTables → repopulate row cache.

Remember: Cassandra finds rows fast, scans columns fast, does not scan rows.

CREATE TABLE users (id timeuuid PRIMARY KEY, lastname varchar,
                    firstname varchar, dateOfBirth timestamp);
INSERT INTO users (id, lastname, firstname, dateofbirth)
  VALUES (now(), 'Berryman','John','1975-09-15');
SELECT dateofbirth, firstname, lastname FROM users;
CQL primary keyInternal mapping
PRIMARY KEY (name)name = row key (partition); each other CQL column = one Cassandra column.
PRIMARY KEY (company, name)company = row key; compound column names: e.g. OSC row: eric:age 38, eric:role ceo, john:age 37…
PRIMARY KEY ((A,B),C,D)(A,B) composite row key; clustering columns C,D prefix column names, e.g. c:d:E, c:d:F.

Collections: set (unique elements), list (ordered, repeats allowed), map (key-value pairs); cannot be part of a primary key. Stored as extra columns: set element in column name (b:myset:1), list uses a time-UUID name, map key in column name (b:mymap:m). Update syntax: myset = myset + {'apple'}, mylist = ['x'] + mylist, mymap['fruit'] = 'apple'.

8ZooKeeper: Why & What

Classic system: one master, many slaves (e.g. HDFS). A fault-tolerant system adds a backup master and a coordination service.

Race conditionTwo processes compete, corrupting data: two people deposit 1 Rs into an account holding 17; both read 17 and write 18 instead of 19.
DeadlockProcesses wait on each other directly or indirectly (P1→P2→P3→P1) and never end.

Coordination needs: group membership, leader election, dynamic configuration (service registry), status monitoring, queuing, barriers, critical sections. Example: several email-indexer processes on different machines need a central, concurrency-safe store to avoid indexing the same email – ZooKeeper's role.

DefinitionZooKeeper is a highly reliable distributed coordination kernel and a replicated service holding metadata of distributed applications (small, performance-sensitive, dynamic, critical). A central key-value store for coordination, running itself on many machines. Uses: locking, synchronization, configuration, leader election, work queues – free from race conditions and deadlocks.

Design goals

Simple – shared hierarchical namespace like a file system of znodes; data in memory → high throughput, low latency.
Replicated – ensemble of servers, each with in-memory state; leader elected at startup; followers serve clients, all updates go through the leader; reply after a majority persisted; 2f+1 machines tolerate f failures.
Ordered – each update stamped with a number reflecting transaction order (basis for synchronization primitives).
Fast – best for read-heavy loads (~10:1); Yahoo! benchmark >10,000 write-dominant ops/s.

Clients keep a TCP connection, get watch events, send heartbeats, and reconnect to another server if it breaks. Servers keep in-memory state plus persistent transaction logs and snapshots.

Data model

Like a highly available file system: data lives in znodes (JSON data, updated whole – no append); reads/writes are atomic; znodes can have children, forming a tree rooted at "/" (e.g. /zoo/duck); "." and ".." are invalid.

Znode typeBehavior
PersistentDefault; stays until deleted (create /name "data").
EphemeralDeleted when the creating session ends (visible to others meanwhile); cannot have children.
Sequentialcreate -s appends a monotonically increasing counter to the name (e.g. /zoo0000000008); each parent keeps a counter.

9ZooKeeper Architecture

Modes: Standalone (one machine; testing only; no HA) and Replicated (ensemble; highly available; tolerates failures while a majority survives).

Phase 1: Leader electionPaxos-like; done when a majority sync with the leader; re-election ~200 ms; leader steps down if majority is lost
→
Phase 2: Atomic broadcastWrites forwarded to leader → broadcast → majority persist → leader commits → client gets success (like two-phase commit; disk before memory)

Election details (Zab – ZooKeeper Atomic Broadcast)

  • Each server takes the next-higher sequence id (via the ZK file system); highest id becomes leader.
  • Naïve failure handling (everyone monitors the leader) causes an election flood. ZooKeeper's way: each process monitors its next-higher-id process; if that was the leader and failed, it becomes leader, otherwise it waits and rechecks.
  • Id conflicts / leader failure mid-election: leader sends NEW_LEADER; each process ACKs at most one leader (highest id); on a majority of ACKs leader sends COMMIT; processes then update their leader variable – safety preserved.
Why majority?3 nodes, leader dies → remaining 2 (majority) elect a leader. 3 nodes, two die → no leader (1/3 is not majority). For a 6-server ensemble split across two data centres, without the majority rule each side would elect its own leader → inconsistency and chaos.

Sessions

Client tries servers from its list until connected; the server creates a session with a timeout. If no request arrives within the timeout the session may expire and ephemeral nodes are lost; the client library sends pings (heartbeats). Sessions survive switching servers; failover is automatic, but operations fail during disconnection. States: CONNECTING → CONNECTED (SyncConnected) ⇄ Disconnected; Expired/close → CLOSED.

10ZooKeeper: Usage

Guarantees: sequential consistency (a client's updates applied in order), atomicity, single system image (a new server won't accept a client until caught up), durability, timeliness (no very stale data).

OperationPurpose

Multi-update batches operations: all succeed or all fail, enabling transactions. APIs: Java and C core; Perl, Python, REST in contrib; synchronous and asynchronous versions.

Watch onTriggered when znode is…
existscreated, deleted, or data updated
getDatadeleted or data updated
getChildrendeleted, or a child created/deleted

Watches fire only once (re-register for more); set by read ops, triggered by write ops (create, delete, setData); ACL ops do not participate. ACL = authentication scheme + identity + permissions; schemes: digest (username/password), sasl (Kerberos), ip.

Server discovery use caseEach server creates an ephemeral znode under /servers (e.g. duck, cow); clients run ls /servers. When duck dies its znode vanishes and the next ls returns only cow.

Other uses: reliable configuration service, distributed lock service (only one process holds the lock). Applications: Yahoo! Fetching Service (crawler configuration metadata, master election), Katta (distributed indexer: group membership, failover, shard assignment), Yahoo! Message Broker (publish-subscribe: topic distribution, failure detection, membership; ephemeral znodes under "nodes", topic znodes with primary/backup).

When not to use: storing big data (copies = number of nodes, all in RAM, network load) and needing extremely strong consistency.

11Quick Revision

Must remember
  • Placement: SimpleStrategy (Random/ByteOrdered partitioner) vs NetworkTopologyStrategy; snitches map IP → rack/DC.
  • Write: commit log → memtable → SSTable (+ index + Bloom filter); compaction; tombstones; hinted handoff; read repair.
  • Gossip membership; PHI accrual detector (PHI 5 ≈ 10–15 s).
  • CAP: pick 2; Cassandra = A+P (eventual, BASE); RDBMS = ACID.
  • Quorum: W+R > N and W > N/2; levels ANY, ONE, QUORUM, LOCAL_QUORUM, EACH_QUORUM, ALL.
  • CQL: row key = partition; compound keys become compound column names; collections not in primary keys.
  • ZooKeeper: znodes (persistent, ephemeral, sequential); ensemble of 2f+1; leader election + atomic broadcast (Zab); majority rule; watches fire once.
