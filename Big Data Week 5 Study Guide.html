1HBase

DefinitionHBase is an open-source NoSQL, distributed, column-oriented store that scales out to 1,000s of commodity servers and petabytes. It runs on HDFS (scalability, fault tolerance, HA), implements Google's BigTable architecture and handles structured, semi-structured and unstructured data. Yahoo! open-sourced it; Facebook uses it. Unlike Cassandra, HBase prefers consistency over availability.

API: Get/Put(row), Scan(row range, filter) for range queries, MultiPut.

Architecture & components

Tables are split into regions served by region servers; regions are divided vertically by column family into stores, saved as files on HDFS. ZooKeeper (a small group running Zab, Paxos-like) provides coordination.

Data model

  • Table â†’ Row (unique row key, byte[], rows stored sorted by key) â†’ Column families (same for every row; a row need not fill all) â†’ column qualifiers (byte[], not declared in advance, may differ between rows; written family:column, e.g. personaldata:Name).
  • Cell = row key + column family + qualifier, holding a value and timestamp. Cell values are versioned (default timestamp; latest returned if unspecified; default 3 versions per column family).
  • Full KeyValue = (row key, family, qualifier, timestamp) â†’ value. Column families are stored in separate files (HFiles) and can be read separately.

HFile: data blocks of (key, value) plus metadata, file info, indices and trailer; each key holds key/value/row lengths, row, family, qualifier, timestamp, key type.

Strong consistency: Write-Ahead LogA write goes first to the HLog, then to the MemStore (log before memory), so a failed RegionServer can replay the HLog (using timestamps) to rebuild MemStore edits on recovery or boot-up.
  • Cross-datacenter replication: one master cluster, other slave clusters replicate the tables; master sends HLogs to slaves; coordination via ZooKeeper (/hbase/replication/state, /peers, /rs).
  • Auto-sharding: the region is the unit of scalability: sorted contiguous rows, spread "randomly" over RegionServers, moved for load balancing/failover, split automatically or manually as data grows. Capacity depends on nodes vs regions per node.
  • Bloom filter: generated when an HFile is persisted, stored at its end and loaded in memory; checks at row + column level; can skip whole store files (useful for grouped data and many misses). Example: for "row-R", block index says yes for 6 files (6 blocks loaded) but Bloom says "Maybe" for only 2 (2 loaded).
  • Fold, Store, Shift: physical layout differs from logical; every value stored with full coordinates (row, family, qualifier, timestamp), columns folded into "row per column"; NULLs cost nothing; versions are extra rows.

Problems of existing approaches

  • Traditional stateful model: pipeline of nodes with mutable state; state lost on node failure â€“ hard to make fault tolerant.
  • Storm: replays unprocessed records â†’ at-least-once, may update state twice, state can be lost. Trident: transactions give exactly-once but per-state transactions to an external database are slow.

3Spark Streaming

Extends Spark for scalable, fault-tolerant, second-latency stream processing with a simple batch-like API. Consumes Kafka, Flume, Twitter, ZeroMQ, Kinesis, TCP sockets, HDFS; pushes results to HDFS, databases, dashboards. (Spark 2.x adds Structured Streaming, Dataset-based.) Part of the ecosystem: Spark SQL, Streaming, MLlib, GraphX, SparkR over Spark Core.

5Fault Tolerance & Performance

  • RDDs remember lineage; input batches are replicated in memory on multiple workers (default factor 2); lost partitions are recomputed on other workers; transformations are exactly-once.
  • Checkpointing to HDFS every ~5â€“10 batches saves state; needs a checkpoint directory in StreamingContext; the driver must be restarted on another node if it fails.
  • Backpressure: spark.streaming.backpressure.enabled, spark.streaming.receiver.maxRate.

6Sliding Window Analytics

Window parametersWindow length = duration of the window; sliding interval = how often the window operation runs. Both must be multiples of the batch interval. A window yields a new DStream with a larger batch size.

Spark window functions (DataFrames/SQL, since Spark 1.4) compute one result per row over a window of rows â€“ unlike aggregates (one result per group) and UDFs (one result per row from that row only). Window spec = partitionBy (grouping; data of a group goes to one machine), orderBy (order within group), frame (boundaries relative to current row).

8Apache Kafka

DefinitionKafka is an open-source, high-performance, real-time messaging system: distributed, partitioned, fault-tolerant, scalable; millions of messages/s to many receivers. Developed at LinkedIn, open-sourced early 2011, Apache top-level project Oct 2012 (0.8.2.1, May 2015).

Streaming platform (Unix-pipe analogy): Kafka Core = distributed durable pipes (hub to transport/store event streams); Kafka Connect = I/O redirection (import/export with other systems); Kafka Streams = the commands (Java library to process streams live).

Use cases: messaging service; real-time stream processing (e.g. to Storm); log aggregation (into HDFS); commit log service for distributed systems; event sourcing (time-ordered events); aggregating user activity (clicks, searches from portals â†’ real-time monitoring + Hadoop offline). Adopted by thousands of companies.

Data model & architecture

ConceptMeaning
MessageUnit of information (log line, stock row, error).
TopicCategory of messages; split into partitions.
PartitionOrdered commit log; each message has an offset; append at one end, consume at other; unit of parallelism; should fit on one server; number of partitions sets parallelism.
ProducerPublishes to an existing topic; decides the partition.
Consumer / groupReads topics; belongs to a consumer group; consumer groups control the messaging model.
BrokerKafka process handling messages; one per machine; cluster = set of brokers; coordinate via ZooKeeper; leader per partition handles delivery and persistence.

Partition distribution: replicated across servers; one leader (controls reads/writes) and followers (replicate); on leader failure a follower becomes leader; ZooKeeper selects the leader.

Queue systemEach message consumed by only one consumer of a group; e.g. consumers 1, 2, 3 get messages (1,4), (2,5), (3,6).
Publish-subscribeEach message goes to all subscribers (each in its own consumer group); each receives 1â€“6 in order.
  • Guarantees: messages from a producer to a topic-partition are appended in order; consumers see them in produced order; replication factor N tolerates Nâˆ’1 server failures.
  • Replication: primary-backup; leader propagates writes and waits for all replicas; a down replica is skipped until it returns.
  • Persistence: Linux file system; relies on OS page cache; data written immediately to file; messages grouped as message sets (compressible); standard binary format across producers, brokers, consumers.
