2Parameter Server & Stale Synchronous Parallel

Parameter Server (PS)An ML framework that distributes a model over multiple machines (PS shards). Training state is stored in shards with asynchronous updates. Two operations: Pull (query parts of the model) and Push (update parts). Update equation: Wi ← Wi + Δ (e.g. stochastic gradient descent, collapsed Gibbs sampling for topic models); push updates are aggregated by addition.
  • Key-value API for workers: get(key) → value, add(key, delta) (distributed shared memory). Extensions: multiple keys (matrix), multiple "channels", push/pull of recent copies, optional blocking, clock-based blocking.
  • Data-parallel learning: split data across worker machines; different parts of the model sit on different servers; workers fetch the part they need.
  • Flexible: used for LDA (topic model), matrix factorization (MF), CNN, DNN (Petuum, YahooLDA, DistBelief…). Glint adds parameter servers to Spark.

Why not MapReduce for iterative ML?

Costs of iteration in MapReduce: the same training data is repeatedly loaded and output is redundantly saved between stages.

The problem: networks are slow

  • Solution 1 – cache synchronization: workers cache parameters and send sparse changes to the model.
  • Solution 2 – asynchronous execution: avoids barriers (no idle waiting) and enables more frequent coordination, but lacks theoretical guarantees because of arbitrary network delays and stragglers.
Stale Synchronous Parallel (SSP)Global clock t; a worker's "get" may be out of date but not older than a staleness bound s (τ). The fastest and slowest workers may not drift more than s clocks apart (the fast worker blocks). SSP interpolates between BSP and async and subsumes both (BSP = staleness 0); workers mostly run at their own pace; implemented efficiently by caching parameters. Delayed SGD: xt+1 = argminx∈X ‖x − (xt − ηt gt−τ)‖ – a gradient step with a stale gradient plus projection onto the feasible space.

Consistency matters: in LDA on 32 machines (256 cores), a suitable delay (SSP) gives a big speed-up over strong consistency (BSP) by cutting network waiting time; SSP outperforms BSP and pure async in convergence.

3PageRank

Big graphs: social-scale (1 billion vertices, 100 billion edges), web-scale (50 billion vertices, 1 trillion edges), brain-scale (100 billion vertices, 100 trillion edges). Web pages grew from 150 million (1998) to 1000 billion (2008), diverse in topic and quality – hence the need to rate page importance objectively and mechanically from link structure.

PageRankDeveloped by Larry Page and Sergey Brin (project started 1995, prototype 1998) – Google's first algorithm to rank search results. Links from many pages, or from a high-rank page, give a high rank. PR(E) denotes the PageRank of E. Equivalent to a random surfer; ranks form the stationary distribution x* = (x*)TP.
  • Basic form: PR(u) = Σv∈Γ(u) PR(v)/L(v) – L(v) = number of outbound links of v, Γ(u) = set of pages linking to u.
  • With damping factor d (0.85): PR(pi) = (1−d)/N + d · Σpj∈Γ(pi) PR(pj)/L(pj), N = total pages (i.e. 0.15/N + 0.85·sum).
  • Iteration: start with PR(p;0) = 1/N; update each step; stop after a fixed number of iterations or at convergence, Σ|PR(t+1) − PR(t)| < ε.
  • Stationary distribution theorem: a unique stationary distribution exists if (1) there is a path from every node to every node, and (2) the greatest common divisor of all cycle lengths is 1.

Example: four pages A, B, C, D, each initial 0.25. If B, C, D all point only to A: PR(A) = 0.25·1 + 0.25·1 + 0.25·1 = 0.75. With B→A, C→A, D→A having outgoing weights ½, 1 and ⅓: PR(A) = 0.25(½ + 1 + ⅓) = 0.458.

4PageRank at Scale: MapReduce & Pregel

FrameworkHow it worksLimitation
MapReduceMap: for vertex n emit the vertex itself and p = PageRank/|adjacency list| to each neighbor. Pregel (Google)Batch algorithms on large graphs; each vertex program runs in parallel in supersteps: process messages from the previous iteration, send messages to neighbors, set the active flag. Loop until no vertex is active or max iterations. Open source: Apache Giraph, Stanford GPS, JPregel, Hama.Bulk-synchronous barriers.
// PageRank in Pregel (Compute)
if (superstep() >= 1) { sum = Σ msgs; value = 0.15/NumVertices() + 0.85 * sum }
if (superstep() < 30) SendMessageToAllNeighbors(value / numOutEdges)
else VoteToHalt()

Worked example: five vertices start at 0.2; each step rank = 0.15/5 + 0.85·sum(incoming) – values evolve (e.g. 0.03, 0.172, 0.34, 0.426, 0.03 → 0.03, 0.0513, 0.095, 0.794, 0.03), concentrating rank on the best-linked vertex.

GraphX (built on Spark Core, with Spark SQL, Streaming, MLlib) measures connectedness, degree distribution, average path length and triangle counts; applies PageRank; supports the Pregel API; introduces VertexRDD, EdgeRDD, Edge, triplets.

Graph-parallel pattern (Gonzalez et al., OSDI'12)A vertex's computation depends only on its neighbors: Gather information from neighbors → Apply an update to the vertex property → Scatter information to neighbors.
PageRank: R[i] = 0.15 + Σ wji·R[j]. Shortest path: D[i] = 1 + min D[j]. Cluster coefficient: 2·#Triangles[i] / (Deg[i](Deg[i]−1)) (triangle counting measures local-community cohesiveness: more triangles = stronger community).
AbstractionStyle
Pregel (push)"Think like a vertex"; vertex programs interact by sending messages to out-neighbors.
GraphLab (pull)Vertex programs directly read adjacent vertices and edges; data movement managed by the system, not the user.

Both run iterative bulk-synchronous execution (compute → communicate → barrier), used by Pregel, GraphLab, Giraph. They expose specialized graph APIs and exploit graph structure for orders-of-magnitude gains over general data-parallel systems. Graph-parallel algorithms: collaborative filtering (ALS, SGD), structured prediction (belief propagation, Gibbs sampling), semi-supervised ML, community detection (triangle counting, K-core, K-truss), graph analytics (PageRank, shortest path, coloring).

6GraphX: Unified Approach & Design

GraphX ideaA new API that blurs the distinction between tables and graphs and a system combining data-parallel and graph-parallel execution. Encode graphs as distributed tables, express graph computations in relational algebra, and reduce graph-system optimization to distributed joins and incremental materialized maintenance. Tables and graphs are composable views of the same physical data.
  • Property graph: a Vertex Property Table (id → property, e.g. rxin → Student) plus an Edge Property Table (source, destination, property, e.g. Friend, Advisor).
  • Distributed representation: partitioned by a 2D vertex-cut heuristic into parts; stored as a Vertex Table, Routing Table and Edge Table (RDDs).
  • Operators: inherits all Spark RDD operators (map, filter, groupBy, join, reduceByKey…); graph operators: table views vertices, edges, triplets; reverse, subgraph, mapV, mapE; joinV, joinE; and mrTriplets.
  • triplets = vertex info joined with edge info; mrTriplets = map-reduce over triplets (map per edge, reduce grouped by destination id) – e.g. "age of the oldest follower of each user": map emits (dst, src age), reduce takes the maximum.

7GraphX Optimizations & Performance

OptimizationEffect
Mirror cacheVertex properties cached locally beside the edge table for iterative mrTriplets.

Join eliminationSkip joins for unused triplet fields (PageRank needs only the source attribute) – 2× less communication than a three-way join.
Indices & bitmaps; reuseSpeed joins and subgraph construction; reuse routing tables, edge adjacency data and indices across graphs.
  • Performance: PageRank on LiveJournal (69M edges): GraphX faster than Hadoop and Giraph but ≈ 3× slower than GraphLab; on Twitter (1.5B edges) ≈ 2× slower than GraphLab – due to Scala/Java overhead (garbage collection) and no shared-memory parallelism. An integrated GraphX pipeline (Wikipedia XML → top 20 pages) beats combining separate systems (e.g. GraphLab + Spark).
  • Code size: GraphX engine ≈ 3575 lines on Spark; PageRank, connected components, SVD etc. need only ~5–120 lines. Status: alpha in Spark 0.9.
  • Real-world graph properties: power-law degree distribution (top 1% of vertices touch ~50% of edges); 51% of vertices are updated only once in PageRank.
  • Use cases: recommendation via low-rank matrix factorization on bipartite user-item graphs (Netflix); behavior prediction (Conditional Random Fields, belief propagation); community discovery by triangle counts. Standard pipeline: raw XML → ETL → initial graph → slice subgraph → compute (PageRank) → post-process (top users).
  • Conclusion: a standard graph algebra matters for graph systems as SQL did for databases; research directions: dynamic (time-evolving) graphs and serving graph data to external systems.

9Quick Revision

Must remember
  • Parameter server: pull/push, W ← W + Δ, get/add key-value API, sharded model, async updates.
  • BSP (barriers, staleness 0) ↔ async (no guarantee); SSP bounds staleness by s clocks and subsumes both.
  • PageRank = (1−d)/N + d·Σ PR/L, d = 0.85; stop at fixed iterations or convergence; unique stationary distribution needs strong connectivity + gcd of cycles = 1.
  • MapReduce PageRank reshuffles the whole graph each iteration; Pregel uses vertex supersteps, messages and vote-to-halt.
  • Graph-parallel = Gather → Apply → Scatter; Pregel pushes messages, GraphLab pulls neighbor data.
  • GraphX = tables + graphs unified: vertex/edge/routing tables, triplets, mrTriplets, 2D vertex cut; optimizations: mirror cache, active-edge index, join elimination.
  • Flight case: 305 airports, 5366 routes, ATL degree 173, PageRank top ATL/DFW/ORD/MSP/SLC.
