1Why Spark?

DefinitionSpark is a fast, expressive cluster computing system compatible with Apache Hadoop, originally developed at UC Berkeley's AMPLab (2012). It works with any Hadoop-supported storage (HDFS, S3, SequenceFile, Avro…).

Efficiency comes from in-memory computing primitives and general computation graphs; usability from rich APIs (Java, Scala, Python; R in libraries) and an interactive shell. Claims: up to 100× faster, often 2–10× less code.

Limitations of MapReduce

  • Map outputs and intermediate results are saved to HDFS for fault tolerance – an expensive disk save that degrades performance.
  • Costly for iterative and interactive applications; lacks efficient data sharing.
  • This led to specialized frameworks: Bulk Synchronous Processing (Pregel), iterative MapReduce.

Spark ideas: not limited to the map-reduce model; use system memory, avoid saving intermediate results to disk, cache data for repetitive queries (e.g. machine learning); stay compatible with Hadoop.

Ways to run: local multicore (just a library), EC2 scripts, private cluster via Mesos, YARN or Standalone mode. Applications: Twitter spam classification, EM traffic prediction, K-means, ALS matrix factorization, in-memory OLAP on Hive data, SQL on Spark.

2RDDs & Fault Tolerance

Resilient Distributed DatasetAn immutable (read-only), partitioned collection of records spread across the cluster, built through coarse-grained transformations (map, join…), automatically rebuilt on failure, and cacheable in memory (different storage levels; fallback to disk).
TypeNatureExamples
TransformationsLazy; build a new RDD from other RDDs through deterministic operationsmap, filter, flatMap, groupBy, join
ActionsReturn a value or export data; trigger executioncount, collect, take, reduce, save

Programmers also control partitioning and persistence (cache in RAM or disk).

Fault tolerance by lineageRDDs log the coarse-grained transformations that built them (e.g. HadoopRDD → FilteredRDD → MappedRDD). A lost partition is simply recomputed from lineage – no cost if there is no failure.

Log-mining example: load errors, cache() them, then run repeated searches. 1 TB scanned in 5–7 s vs 170 s from disk.

lines = spark.textFile("hdfs://...")
errors = lines.filter(lambda s: s.startswith("ERROR"))
messages = errors.map(lambda s: s.split('\t')[2])
messages.cache()
messages.filter(lambda s: "foo" in s).count()

3Scala Essentials

Scala is a high-level, statically typed language for the JVM, object-oriented + functional, speed comparable to Java, with type inference and full Java interoperability. Spark was originally written in Scala; interactive shells exist in Scala and Python only (standalone programs: any language). Java/Scala are faster (static typing); Python does well for numerics with NumPy.

var x = 7        // mutable, inferred
val y = "hi"     // read-only
def square(x: Int): Int = x * x
var arr = new Array[Int](8)
var lst = List(1, 2, 3)
arr(5) = 7       // indexing with ()
list.map(_ + 2)          // List(3,4,5)
list.filter(_ % 2 == 1)  // List(1,3)
list.reduce(_ + _)       // 6
// (x: Int) => x + 2   full closure
// x => x + 2          inferred

List is immutable, so these leave the original unchanged. Other Seq methods: flatMap (one-to-many), exists, forall, groupBy, sortBy.

4Spark Operations

The SparkContext (sc) is the main entry point (auto-created in shells). Shell mode is set by MASTER: local (1 thread), local[2], or spark://host:port (standalone cluster). Standalone programs create it with (masterUrl, app name, sparkHome, list of JARs/files to ship).

  • Parallelism: pair operations take an optional task-count argument (reduceByKey(f, 5)) or set spark.default.parallelism.
  • Closures: external variables are shipped to the cluster; each task gets a new copy (updates not sent back); must be Serializable/Pickle-able; don't use fields of an outer object (ships the whole object → NotSerializableException). Fix: copy to a local variable first, e.g. val param_ = param.

5Job Execution

Spark runs as a library inside your application (one instance per app). The Driver holds the SparkContext; a cluster manager (Standalone, Mesos, YARN) allocates Workers/Executors, which run tasks and hold the cache; storage is accessed via Hadoop InputFormat (HDFS, HBase, S3, Cassandra, Avro).

RDD objectsbuild operator DAG
→
DAGSchedulersplit into stages of tasks; submit each stage as ready
→
TaskSchedulerlaunch tasks via cluster manager; retry failed/straggling
→
Workerexecute tasks; block manager stores/serves blocks

DAG (Directed Acyclic Graph): source → transformations → RDDs → action; it is Spark's execution plan and scales automatically over executors. The scheduler supports general task graphs, pipelines functions where possible, is cache-aware (reuse and locality) and partitioning-aware to avoid shuffles. Shuffle = exchange, partition, sort across executors.

Job example: errors.cache() then two filter(...).count() actions – the first action loads and caches blocks on workers; the second reuses the cache.

Build & submit: sbt package, then spark-submit --master local --class GvaWeather target/…jar. Hadoop compatibility: reuses InputFormat/OutputFormat; textFile for filesystems, hadoopRDD with any JobConf.

6PageRank in Spark

Good example of a complex, multi-stage, iterative algorithm that benefits from in-memory caching. Idea: links from many pages, or from a high-rank page, give high rank.

Algorithm1. Start each page at rank 1. 2. Each iteration, page p contributes rankp / |neighborsp| to its neighbors. 3. New rank = 0.15 + 0.85 × Σ contributions.
Example: contributions 1 + 0.5 + 0.5 → 0.15 + 0.85 × 2 = 1.85. Ranks evolve 1.85, 0.58, 1.0, 0.58 → 1.31, 0.39, 1.72, 0.58 → final 1.44, 0.46, 1.37, 0.73.
val links = // RDD of (url, neighbors)
var ranks = // RDD of (url, rank)
for (i <- 1 to ITERATIONS) {
  val contribs = links.join(ranks).flatMap {
    case (url, (links, rank)) => links.map(dest => (dest, rank/links.size)) }
  ranks = contribs.reduceByKey(_ + _).mapValues(0.15 + 0.85 * _)
}

9Design of Key-Value Stores

Key-value abstraction: key → value (item number → item info; tweet id → tweet; account number → account). It is a distributed dictionary (insert, lookup, delete by key, like a hash table) and reuses techniques from P2P Distributed Hash Tables (DHTs).

AspectRDBMS (e.g. MySQL)Key-value / NoSQL ("Not Only SQL")
StorageTables, entire row stored togetherTables ("column family" in Cassandra, "table" in HBase, "collection" in MongoDB); typically a column/column group stored together
SchemaFixed, structured; primary/foreign keysMay be schemaless; columns can be missing per row; no foreign keys; joins often unsupported
QuerySQL, joinsget(key), put(key, value) plus extensions (CQL in Cassandra); can have index tables
Why RDBMS mismatches today's workloadsData is large and unstructured (hard to define schemas); millions of clients do random reads/writes, sometimes write-heavy; foreign keys are rarely needed and joins infrequent (an overhead).

Needs: speed, avoid single point of failure (SPOF), low TCO (total cost of operation/ownership), fewer administrators, incremental scalability – scale out, not scale up.

Scale upReplace with more powerful machines; traditional; not cost-effective (above price-curve sweet spot); frequent replacement.
Scale outAdd more COTS (Components Off The Shelf) machines incrementally; cheaper; phase in newer machines and phase out older; used by most data centers and clouds.

Column-oriented storage: range searches within a column are fast without fetching the whole database – e.g. "blog_ids updated in the past month": search the last_updated column and fetch the matching blog_id column only.

10Apache Cassandra: Key → Server Mapping

Cassandra is a distributed key-value store intended to run in a datacenter (and across DCs); designed at Facebook, now an Apache project. Users include IBM, Adobe, HP, eBay, Ericsson, Twitter, PBS Kids; Netflix uses it to track positions in videos.

Partitioner: the key→server mapping. Cassandra uses a ring-based DHT without finger tables or routing, one ring per datacenter. 11Quick Revision

Must remember
  • Spark fixes MapReduce's disk-heavy intermediate results for iterative/interactive jobs (up to 100×).
  • RDD = immutable, partitioned, lazily transformed; actions trigger execution; recovery by lineage.
  • Transformations: map, filter, flatMap, reduceByKey, groupByKey, join, cogroup. Actions: count, collect, take, reduce, save.
  • Execution: Driver/SparkContext → cluster manager → executors; DAGScheduler (stages) → TaskScheduler (tasks).
  • PageRank: rank = 0.15 + 0.85 × Σ(rank/|neighbors|).
  • Libraries: SQL, Streaming, MLlib, GraphX.
  • Key-value stores: get/put, no fixed schema, column storage, scale out; Cassandra = ring partitioner with primary and backup replicas.
