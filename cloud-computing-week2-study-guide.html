Key subtletyContrary to popular belief a private cloud may exist off premises and be managed by a third party. Hence two private scenarios: on-site private (at the customer's premises) and outsourced private (server side outsourced to a hosting company). Community clouds likewise split into on-site and outsourced.

Public cloud: characteristics and issues

  • Resources and clients: provider resources potentially very large; links over the public Internet; a diverse pool of clients (and possibly attackers).
  • Hidden workload locations: provider may migrate workload or data at any time (e.g. to cheaper data centres) unless it offers optional location-restriction policies.
  • Multi-tenancy risk: a machine may be shared by competitors or adversaries, giving reliability and security risk.
  • Network dependency: access depends on Internet infrastructure (DNS servers, routers, inter-router links).
  • Limited visibility and control: provider operations and software are proprietary; a subscriber cannot verify that data was completely deleted.
  • Elasticity: illusion of unlimited resources; flexible workload movement. Low up-front cost of migration. Restrictive default SLAs (limited promises).

  • Multi-tenancy in private clouds: workloads of different clients share systems and networks, separated only by access policies; a software or policy flaw can expose them to each other.
  • Community access policy may be complex: with N members, each must decide how to share its local resources with the others. Policy techniques: role-based access control (RBAC), attribute-based access control. At least one member must provide cloud services; others may only consume.
  • Hybrid: performance, reliability and security vary with the clouds chosen; can be extremely complex, and constituent clouds may join and leave over time.

2IaaS in Depth

What a subscriber gets: virtual computers, network-accessible storage, network components such as firewalls, and configuration services. Fees are typically per CPU-hour, GB stored per hour, bandwidth consumed, network infrastructure used (e.g. IP addresses) per hour, and value-added services (monitoring, automatic scaling).

Interaction: the provider holds a pool of VMs (vm1…vmN) and allocates them to clients (e.g. A gets vm1–vm2, B gets vm3, C gets vm4–vm6); the provider retains the rest.

Scope of control

LayerProviderSubscriber
Application, Middleware, Guest OSNo controlTotal control (free to load any supported OS into the VM)
Hypervisor (VMM)Administrative controlMakes requests only
HardwareTotal controlNo control

The OS layer splits into two: the lower, more privileged hypervisor/VMM and the higher guest OS running in a VM. A hypervisor synthesizes VMs, each "an efficient, isolated duplicate of a real machine"; the subscriber administers the VM (power on/off, peripherals) by commands over the network.

Logical IaaS cloud architecture: three-level hierarchy

Cloud Managertop level; central control
→
Cluster Managersmiddle level; manage clusters (may be geographically distant)
→
Computer Managersbottom level; run hosts that create VMs

Subscriber queries and commands enter at the top and flow down. Within a cluster, computer managers are connected by a high-speed network (LAN); cluster managers connect over a WAN.

ComponentRole
Cloud ManagerPublic access point: subscribers sign up, manage rented resources and access stored data. Authenticates subscribers, generates/validates access credentials for VMs, does top-level resource management, and decides whether free resources can satisfy a request.
Data Object Storage (DOS)Stores subscriber metadata such as user credentials and OS images; usually a single service per cloud.
Cluster ManagerRuns a collection of computers on high-speed LANs. Receives allocation commands and queries from the Cloud Manager, calculates whether the cluster can satisfy them, queries Computer Managers for availability, then (as directed) instructs them to allocate and reconfigures the virtual network for uniform subscriber access. Connected to Persistent Local Storage (PLS), which gives VMs persistent disk-like storage.
Computer ManagerRuns on each computer; uses virtualization to provide VMs; tracks how many VMs run and can still start; uses the hypervisor's command interface to start, stop, suspend and reconfigure VMs.

3Virtualization

DefinitionVirtualization (broad: memory, storage, network…) lets one computer do the job of several by sharing a single hardware platform across multiple environments. Focus here: platform virtualization. A non-virtualized system has one OS controlling all hardware; a virtualized system adds a virtualization layer so several virtual containers (each with OS and apps) run on one physical platform.

Different from dual-boot: both OSes run simultaneously and are completely isolated (e.g. Windows and Linux on one laptop).

Hypervisor / VMM and Popek–Goldberg

A hypervisor runs the guest OS directly on the CPU (works only if guest and host share the instruction set). The guest runs in user mode, so privileged instructions must be intercepted or replaced. Popek and Goldberg (CACM 1974) set three goals:

Equivalence: VM indistinguishable from the underlying hardware
Resource control: VM in complete control of virtualized resources
Efficiency: most VM instructions run directly on the CPU without the hypervisor
  • Privileged instructions trap if executed in user mode. Sensitive instructions change underlying resources (I/O, page tables) or reveal the privilege level; they are control sensitive or behavior sensitive.
  • Theorem: a VMM can be constructed for a conventional third-generation computer if the set of sensitive instructions is a subset of the privileged instructions; then most instructions run directly and sensitive ones trap to the hypervisor, which emulates them. It is recursively virtualizable if virtualizable and a VMM without timing dependencies can be built.
  • Xen example: Domain 0 (privileged, device drivers) and Domain U (guest, split device drivers) on the Xen hypervisor over hardware.

4Network Virtualization

DefinitionA networking environment that allows multiple service providers to dynamically compose multiple heterogeneous virtual networks that co-exist in isolation, deploy customized end-to-end services on the fly and manage them for end users, by sharing and using network resources leased from multiple infrastructure providers. Simply: making one physical network appear as multiple logical ones.

Why: the Internet is almost "paralyzed" by makeshift fixes (e.g. overlays); a clean-slate architecture is needed but a one-size-fits-all design is hard and the future is unpredictable, so build an open, expandable "all sizes fit into one" architecture and a testbed for future protocols.

Related concepts: VPN (connects distributed sites; not customizable enough) · active and programmable networks (customized functions, programmable interfaces) · overlay networks (application-layer virtual networks; not flexible enough).

Business model: playersInfrastructure Providers (InPs) manage physical networks · Service Providers (SPs) create/manage virtual networks and deploy end-to-end services · End users buy services · Brokers mediate. Relationships via SLA, NPA, SIA, IIA, EIA.
ArchitecturePhysical nodes/links host virtual nodes/links of VN1, VN2… owned by SP1, SP2; supports recursion (child virtual network over a parent) and revisitation of virtual nodes.

Typical approach: networking technology (IP, ATM) · layer of virtualization (architectural domain: network resource management, spawning networks) · level of virtualization (node virtualization, full virtualization).

5XML Basics

What is XMLeXtensible Markup Language: a syntax for encoding text-based data. Text-based (printable Unicode characters; no explicit binary data). Extensible (define your own elements within the syntax rules). Universal format: syntax rules ensure all XML software must handle a given piece of XML identically. "XML" has also come to mean a family of tools, standards and application dialects built on it. It descends from SGML, is supported by the W3C, separates content from presentation, and is designed to describe data.
<?xml version="1.0" encoding="iso-8859-1"?>      <!-- XML declaration -->
<partorders xmlns="http://myco.org/Spec/partorders">
  <order ref="x23-2112-2342" date="25aug1999-12:34:23h">
    <desc> Gold sprocket grommets </desc>
    <part number="23-23221-a12" />
    <quantity units="gross"> 12 </quantity>   <!-- tags/element; units = attribute -->
  </order>
</partorders>
  • Data model is a tree: hierarchical, structured; root partorders → order (attributes ref, date) → desc (text), part, quantity, delivery-date.
  • Why it is this way: simple, with strict syntax rules that eliminate errors; syntax defines hierarchical structure and names parts, so data is self-describing; extensible (unlike HTML, you create your own tags); designed for a distributed environment; different tag sets can be mixed and the result is still reliably processed.

Parser processing model

→
Parser(+ DTD)
→
Parser interface
↔
XML-based application
  • The parser must verify the data is syntactically correct, i.e. well-formed: the minimal requirement to "be" XML. If not well-formed it MUST stop and throw an exception (required by XML 1.0).
  • Entities: an internal entity (declared in the DOCTYPE with <!ENTITY name "…">) encodes reusable markup, referenced as &name;. An external entity lives in another file (SYSTEM "URL") so multiple resources share it. The parser replaces every reference recursively and hands the resolved data to the application.
  • Two parser types: a validating parser must retrieve all entities, process all DTD content, check the document against the DTD's rules, and stop with a failure if it cannot. A non-validating parser tries to retrieve entities but stops DTD processing at the first one it cannot find; this is not an error, and it passes the data and unresolved entity names to the application. Many parsers support either mode.
  • Characters: XML restricts whitespace characters (e.g. EBCDIC NEL not allowed); characters outside the charset use character references (&#9824; = Unicode character 9824, spades); binary data must be encoded as printable characters.

XSLT model: style sheet and XML data each go through an XML parser (with schema) into the XSLT processor, which outputs XML.

XML messaging

  • Use XML as the message format between systems. Advantages: common, self-describing syntax (easier to parse); reuse existing transports (HTTP, HTTPS, SMTP, MQ, IIOP/CORBA, JMS).
  • Requirements: shared understanding of dialects (a registry/namespace to identify them) and shared acceptance of the messaging contract.
  • Disadvantages: asynchronous transport with no guarantee of delivery or that the partner accepts the contract; messages are about 10× larger than binary (can compress).
  • XML over HTTP: HTTP POST with Content-type: application/xml. Wrapper standards: XML-RPC (simple encoding of a method name and parameters) and SOAP (more complex; schemas for interfaces, message handling/proxying; core of Microsoft .NET).

8Web Services & SOA

Web service (W3C)A software application identified by a URI, whose interfaces and bindings can be defined, described and discovered as XML artifacts. Revisited: a component that communicates via open protocols (HTTP, SMTP), processes XML messages framed using SOAP, describes messages with XML Schema, provides an endpoint description using WSDL, and can be discovered using UDDI.
Vendor views: Microsoft, programmable application logic via standard Internet protocols; IBM, an interface describing network-accessible operations through standardized XML messaging; Sun, components spontaneously discovered, combined and recombined to solve a request.

History: structured programming → object-oriented → distributed computing → EDI → World Wide Web → Web services.

  • Distributed computing: N-tier applications (e.g. UI, business logic, database on three machines) need communicating components (DCE, CORBA, DCOM, RMI); interoperability across vendors/platforms is limited in proprietary technologies.
  • EDI: computer-to-computer exchange of business documents in standard formats agreed by both parties. Benefits: lower operating cost, fewer errors (no data entry), higher productivity, faster trading cycle. Web services give EDI-like capability that is simpler and cheaper, can work alongside EDI or let organizations phase it out.
  • Web services: build applications from existing components modularly (network as one library of components); open, text-based standards that are easier to debug than binary; separate visual from non-visual parts (browser or desktop client).
Problem solvedHow
InteroperabilityDCOM was bound to Windows, RMI to Java; open standards let any two components communicate
Firewall traversalCORBA/DCOM used non-standard ports; web services use HTTP (port 80), which most firewalls allow
ComplexityDeveloper-friendly, text-based standards across languages/platforms; adopted incrementally, lowering cost and disruption

9SOAP, WSDL, UDDI & Security

SOAP (Simple Object Access Protocol)

  • Format for sending messages between programs over the Internet; XML-based, platform- and language-independent, simple and extensible. Mainly uses HTTP as transport (HTTP message carries the SOAP message as payload). Stateless, one-way, though applications can build richer interaction patterns.
  • Message: request invokes a method on a remote object; response returns the result. A SOAP envelope wraps the application-specific message; namespace prefixes separate the two vocabularies.
Building blockStatusContents
EnvelopeRequiredIdentifies the XML document as a SOAP message
HeaderOptionalHeader information
BodyRequiredCall and response information
FaultOptionalErrors that occurred while processing
POST /InStock HTTP/1.1  Host: www.stock.org  Content-Type: application/soap+xml
<soap:Envelope xmlns:soap="http://www.w3.org/2001/12/soap-envelope">
  <soap:Body xmlns:m="http://www.stock.org/stock">
    <m:GetStockPrice><m:StockName>IBM</m:StockName></m:GetStockPrice>
  </soap:Body>
</soap:Envelope>       → response returns <m:GetStockPriceResponse><m:Price>34.5</m:Price>…
  • Why SOAP: other technologies failed on the Internet: Unix RPC needs binary-compatible Unix at each end, CORBA needs compatible ORBs, RMI needs Java, DCOM needs Windows. SOAP is a platform-neutral XML wire format with no restriction on endpoint technology.
  • Characteristics: extensibility (security, WS-routing), neutrality (any transport: HTTP, SMTP, TCP), independence (any programming model).
  • Usage models: RPC-like exchange (method name and parameters; return values) but not required; any XML body is allowed, e.g. send a purchase order to a B2B partner and receive a shipping/exception report.
  • Security: can use HTTP over SSL; since SOAP can run over other protocols (e.g. SMTP), WS-Security defines a complete encryption system. Security architecture: WS-Security on SOAP, with WS-Policy, WS-Trust, WS-Privacy, WS-Secure Conversation, WS-Federation, WS-Authorization above.

WSDL (Web Service Definition Language)

XML vocabulary describing web services and their capabilities; the contract between the service and the client. It specifies what a request must contain and what the response looks like, where the service is available and which protocol is used. A WSDL document is simple XML with four major elements:

types: data types used
message: messages used
portType: operations performed
binding: communication protocols used (e.g. SOAP over HTTP)

UDDI (Universal Description, Discovery and Integration)

  • A framework for XML-based registries: repositories of documents describing business data, with search. Businesses publish information about themselves and their services; the registry can be queried by SOAP messages and gives access to WSDL documents.
  • Roles: Service registry (publish and locate, "like telephone yellow pages"), service provider (publishes through the registry), service requestor (finds via the broker, binds to the provider).
  • Use case: a business registers via an ASP with the UDDI Business Registry (UBR); marketplaces and search engines query it, cache data and bind to its services; consumers then discover it.
  • Benefits: discover the right business among millions; define how to enable commerce afterwards; reach new customers; expand offerings and market reach.

10Quick Revision

Must remember
  • Deployment: public (open, provider premises), private (single organization; on-site or outsourced), community (shared concerns; RBAC policies), hybrid (two or more clouds with portability, complex, changing). Private on-site = significant-to-high cost, limited resources; outsourced = modest-to-significant cost, extensive resources, two perimeters.
  • IaaS control: provider has total hardware control and admin control of hypervisor; subscriber controls guest OS, middleware, applications. Architecture: Cloud Manager → Cluster Managers (with PLS) → Computer Managers; DOS stores credentials and OS images.
  • Virtualization: Popek–Goldberg goals (equivalence, resource control, efficiency); VMM possible when sensitive ⊆ privileged instructions. Full (binary translation, slow, portable) · para (modified guest, specialized API) · hardware-assisted (Intel VT/AMD-V, unmodified guest, Ring 0).
  • Network virtualization: InPs, SPs, end users, brokers; recursion, revisitation, inheritance, concurrence; goals include flexibility, isolation, programmability, heterogeneity, legacy support.
  • XML: well-formed vs valid; DTD (declares entities) vs Schema (pure XML, data types); namespaces via xmlns; validating vs non-validating parser.
  • Processing: SAX (event, fast, low memory) · DOM (tree, slow, memory-hungry) · JDOM/dom4j (Java) · XSLT (transform XML to XML).
  • Web services: SOA triangle (provider, requestor, registry) with publish, find, bind; XML + SOAP + WSDL + UDDI; solves interoperability, firewall traversal, complexity.
  • SOAP: envelope (required), header (optional), body (required), fault (optional); stateless, mainly over HTTP. WSDL: types, message, portType, binding. UDDI: yellow pages for services.
