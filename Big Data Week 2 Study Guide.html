1HDFS: Introduction & Design

Hadoop provides a distributed file system and a framework for analysing very large data sets using the MapReduce paradigm. Data and computation are partitioned across thousands of hosts and computations run in parallel close to the data. Capacity, storage and IO bandwidth scale by simply adding commodity servers. Yahoo! clusters span 25,000 servers storing 25 PB (largest cluster: 3,500 servers). Yahoo! contributed about 80% of Hadoop's core (HDFS, MapReduce).

2HDFS Architecture

Single NameNode (master) – manages namespace, regulates client access, tracks where blocks are on DataNodes; holds metadata (name, replicas, e.g. /home/foo/data, 3).
Multiple DataNodes – typically one per node, using local storage; manage storage, serve read/write requests, and create/delete/replicate blocks on NameNode instruction.
Hadoop 2.0 improvements HDFS Federation: multiple NameNodes and namespaces. A single NameNode (original design) becomes a bottleneck with thousands of nodes and billions of files. Benefits: namespace scalability, performance, isolation. Data is stored in block pools – one pool per NameNode/namespace – spread across all (common) DataNodes.
High Availability: redundant NameNodes. Heterogeneous / archival storage: ARCHIVE, DISK, SSD, RAM_DISK.

3Block Size & Small Files

Default block size is 64 MB (often raised to 128 MB by workload); good for large files. Block count = file size ÷ block size. Example: 10 GB file → 10 × 1024 / 64 = 160 blocks. Block count affects:

  • NameNode memory – every file/block is an object (~150 bytes each); a billion objects ≈ 300 GB. Replication (3×) triples blocks.
  • Number of map tasks – depends on the blocks processed.
  • Network load – DataNode checks are proportional to number of blocks.
Small-files problem10 GB in 32 KB files → 327,680 map tasks: huge queue, start/stop latency of Java processes per task, inefficient disk I/O. Solutions: merge/concatenate files, sequence files, HBase/Hive configuration, CombineFileInputFormat.

6MapReduce 1.0

MapReduce is Hadoop's execution engine; in Hadoop 1.0 it handles both cluster resource management and data processing over HDFS.

JobTracker (master)Receives job from client, breaks it into tasks, allocates tasks to slaves, monitors progress. Unit of execution = job.
TaskTracker (each slave)Runs tasks on local data, reports progress/results to JobTracker. Master = JobTracker + NameNode; slaves = TaskTracker + DataNode.

Example: 20,000 customer records split as 5 chunks of 4,000 across 5 nodes; each finds customers in "Mumbai" in parallel.

7MapReduce Paradigm

DefinitionMapReduce is a programming model and implementation for processing and generating large data sets. Users write map (key/value → intermediate key/value pairs) and reduce (merges all values for the same intermediate key). Run-time automatically handles partitioning, scheduling, machine failures and inter-machine communication, so programmers need no parallel-systems experience.

Why: use 1000s of CPUs without the management hassle – automatic parallelization and distribution, fault tolerance, I/O scheduling, monitoring and status updates. Terms come from functional languages (Lisp): (map square '(1 2 3 4)) → (1 4 9 16), processing records independently; (reduce + '(1 4 9 16)) → 30, combining in batches.

Inputchunks / records

Output
  • Signature: map(k,v) → list(k1,v1); reduce(k1, list(v1)) → v2.
  • Reduce receives values via an iterator so lists too large for memory can be handled; usually 0 or 1 output per call.
  • Each key goes to exactly one reducer; common hash partitioning: reduce# = hash(key) % number_of_reduce_tasks.
  • Distributed file: chunks 16–64 MB, replicated 2–3×, replicas kept on different racks; master (NameNode) holds metadata, clients then talk directly to chunkservers.
map(key, value):            // key: doc name; value: text
  for each word w in value: emit(w, 1)
reduce(key, values):        // key: word; values: iterator of counts
  result = 0
  for each v in values: result += v
  emit(key, result)

Word count: "see bob run", "see spot throw" → map: bob 1, see 1, run 1, see 1, spot 1, throw 1 → shuffle groups the two "see" → reduce: bob 1, run 1, see 2, spot 1, throw 1.

8YARN Scheduler (Hadoop 2.x+)

YARN = Yet Another Resource Negotiator. Each server is a set of containers (fixed CPU + fixed memory; e.g. 8 cores + 16 GB server = containers of 1 core + 2 GB).

ComponentRole
Global Resource ManagerScheduling
Per-server Node ManagerDaemon and server-specific functions
Per-application Application MasterNegotiates containers with RM and NMs; detects task failures of its job

Getting a container: AM needs container → RM allocates on a node (e.g. Node B) → AM asks that NodeManager to start the task → container completion reported.

10Worked Examples

Word-length counting

Map emits (length, word): 3:the, 3:and, 3:you, 4:then … Grouped: 3:[the, and, you], 4:[then, what, when], 5:[steve, where], 8:[savannah, research]. Reduce counts list size → 3:3, 4:3, 5:2, 8:2.

Word-length histogram

Classes: Big 10+ letters, Medium 5–9, Small 2–4, Tiny 1. Map Task 1 (204 words): yellow 17, red 77, blue 107, pink 3; Map Task 2 (190 words): 20, 71, 93, 6. After shuffle and reduce: yellow 37, red 148, blue 200, pink 9. A combiner can pre-sum locally.

Inverted index

Tweets: 1 "I love pancakes for breakfast", 2 "I dislike pancakes", 3 "What should I eat for breakfast?", 4 "I love to eat". Map emits (word, tweet ID); reduce output: pancakes → (1,2), breakfast → (1,3), eat → (3,4), love → (1,4).

Finding common friends

Input Person → friends: A→BCD, B→ACDE, C→ABDE, D→ABCE, E→BCD. Precomputed daily and stored. Map(P → friends) emits (sorted pair of P and each friend) → P's whole friend list. Group by pair, reduce intersects the lists.

map(A → B C D): (A B)→BCD  (A C)→BCD  (A D)→BCD
Group: (A B) → (A C D E)(B C D)   reduce = intersection → (A B) : (C D)
Results: AB→CD, AC→BD, AD→BC, BC→ADE, BD→ACE, BE→CD, CD→ABE, CE→BD, DE→BC

When D visits B's profile, lookup (B D) → common friends A, C, E.

11Quick Revision

Must remember
  • HDFS goals: fault tolerance, portability, large data, high throughput → replication, write-once-read-many, computation to data, relaxed POSIX.
  • Block 64 MB (128 MB common); 10 GB = 160 blocks; ~150 bytes/object on NameNode; small files → too many map tasks.
  • Federation = many NameNodes + block pools; HA = redundant NameNodes; storage types ARCHIVE, DISK, SSD, RAM_DISK.
  • Failure handling: heartbeat, re-replication, checksums, standby NameNode (manual failover default).
  • MR 1.0: JobTracker (master) + TaskTracker (slave), 7 steps; MR 2.0: YARN with RM, NM, AM and containers.
  • Flow: map → shuffle → reduce; partition = hash(key) % reducers; sort needs range partitioning.
