1HBase

Definition

HBase ek open-source NoSQL, distributed, column-oriented store hai jo 1,000s of commodity servers aur petabytes tak scale out kar sakta hai.

Ye HDFS ke upar run karta hai aur HDFS se:

  • Scalability
  • Fault tolerance
  • High availability

inherit karta hai.

HBase Google's BigTable architecture ko implement karta hai aur:

  • Structured
  • Semi-structured
  • Unstructured

data handle kar sakta hai.

HBase ko Yahoo! ne open-source kiya tha aur Facebook ise use karta hai.

Cassandra ke unlike, HBase availability ke comparison mein consistency ko prefer karta hai.

API

  • Get/Put(row)
  • Scan(row range, filter) → range queries
  • MultiPut

Architecture & Components

HBase tables ko regions mein split kiya jaata hai.

Regions ko column family ke according vertically divide kiya jaata hai, jisse stores bante hain.

Ye stores HDFS par files ke form mein save hote hain.

ZooKeeper coordination provide karta hai. Ye ek small group hota hai jo Zab, yani Paxos-like protocol, use karta hai.

Bloom Filter

Jab HFile persist hoti hai, tab Bloom filter generate hota hai.

Ye HFile ke end par stored hota hai aur memory mein load kiya jaata hai.

Bloom filter:

  • Row + column level par checks karta hai.
  • Entire store files ko skip kar sakta hai.
  • Grouped data aur many misses ke case mein useful hai.

Example

Agar "row-R" search karna hai:

Block index ke according 6 files mein possibility hai:

→ 6 blocks load.

Bloom filter ke according sirf 2 files mein "Maybe":

→ only 2 blocks load.

  • NULL values ka koi storage cost nahi.
  • Versions extra rows ki tarah stored hoti hain.

Problems of Existing Approaches

Two Stacks Problem

Same data ke upar batch + streaming ke liye separate stacks use karne padte the:

  • Hadoop/MapReduce → TBs, high latency
  • Storm → 100s MB/s, low latency

Dono ko ek saath achieve nahi kiya jaata tha.

Problems:

  • Different programming models
  • Same functionality ki double implementation
  • Double operational effort

Traditional Stateful Model

Pipeline of nodes hoti thi jinke paas mutable state hota tha.

Agar node fail ho jaaye:

→ State lost.

Isliye fault tolerance difficult hoti thi.

Storm

Storm unprocessed records ko replay karta hai.

Isse:

At-least-once

semantics milti hai.

Lekin same state twice update ho sakti hai aur state lost bhi ho sakta hai.

Trident

Transactions ke through exactly-once provide karta hai.

Lekin external database mein per-state transactions slow hote hain.

Core Idea — Micro-Batching

Streaming computation ko bahut small deterministic batch jobs ki series ki tarah run kiya jaata hai.

Live stream ko:

X-second batches

mein divide karo.

Har batch ek:

RDD

hota hai aur RDD operations ke through process hota hai.

Results bhi batches mein return hote hain.

Batch size approximately 1 second tak low ho sakta hai.

Therefore:

Latency ≈ 1 second

Batch aur stream code ko same system mein rakha ja sakta hai.

↓

↓

Each Interval

↓

Results

Storage / dashboards ko send hote hain.

Kafka:

  • LinkedIn mein develop hua.

Data Model & Architecture

ConceptMeaning
MessageInformation ki basic unit; e.g. log line, stock row, error
TopicMessages ki category; partitions mein divided
PartitionOrdered commit log; har message ka offset hota hai; ek end par append aur doosre end par consume; parallelism ki unit
ProducerExisting topic par messages publish karta hai; partition decide karta hai
Consumer / GroupTopics read karta hai; consumer group ka member hota hai
BrokerMessages handle karne wala Kafka process; generally one per machine

Partition

Partition ko ideally one server par fit hona chahiye.

Number of partitions = available parallelism

Broker

Kafka cluster:

Set of brokers

Brokers coordination ke liye ZooKeeper use karte hain.

Har partition ka ek leader hota hai jo:

  • Delivery
  • Persistence

handle karta hai.

Partition Distribution

Partitions servers ke across replicated hoti hain.

Har partition mein:

  • One leader
  • Followers

hote hain.

Leader:

  • Reads control karta hai.
  • Writes control karta hai.

Followers data replicate karte hain.

Agar leader fail ho jaaye:

→ Ek follower leader ban sakta hai.

ZooKeeper leader select karta hai.

Queue System

Ek message ko ek consumer group ke sirf one consumer ke through consume kiya jaata hai.

Example:

Consumer 1 → Messages 1, 4
Consumer 2 → Messages 2, 5
Consumer 3 → Messages 3, 6

Yaani messages consumers ke beech distribute ho jaate hain.

Publish-Subscribe

Har message all subscribers ko jaata hai.

Har subscriber apne separate consumer group mein hota hai.

Example:

Har subscriber ko:

1, 2, 3, 4, 5, 6

order mein milenge.

Kafka Guarantees

Kafka guarantee karta hai:

  • Producer se topic-partition tak messages order mein append honge.
  • Consumers messages ko produced order mein dekhenge.
  • Replication factor N → N−1 server failures tolerate kar sakta hai.

Replication

Primary-backup model.

Leader:

  • Writes propagate karta hai.
  • All replicas ke response/persistence ka wait karta hai.

Agar koi replica down hai:

→ Usse temporarily skip kiya jaata hai.

Jab replica return karta hai:

→ Replication resume hoti hai.

Persistence

Kafka Linux file system use karta hai.

OS page cache par rely karta hai.

Data immediately file mein written hota hai.

Messages ko message sets mein group kiya jaata hai, jo compress kiye ja sakte hain.

Same standard binary format producers, brokers aur consumers ke across use hota hai.
