1HBase

DefinitionHBase ek open-source NoSQL, distributed, column-oriented store hai jo 1,000s commodity servers aur petabytes tak scale out kar sakta hai. Yeh HDFS par run karta hai (scalability, fault tolerance, HA ke liye), Google's BigTable architecture implement karta hai aur structured, semi-structured aur unstructured data handle karta hai. Yahoo! ne ise open-source kiya; Facebook ise use karta hai. Cassandra ke unlike, HBase availability ke comparison mein consistency ko prefer karta hai.

API: Get/Put(row), Scan(row range, filter) range queries ke liye, MultiPut.

Architecture & components

Tables ko regions mein split kiya jaata hai jinhe RegionServers serve karte hain; regions ko column family ke basis par vertically stores mein divide kiya jaata hai, jo HDFS par files ki tarah save hote hain. ZooKeeper (Zab, Paxos-like protocol run karne wala small group) coordination provide karta hai.

RegionAvailability aur distribution ki basic unit: sorted, contiguous key range (e.g. R1: smithj–yyyyy).

Data model

  • Table → Row (unique row key, byte[], rows key ke according sorted) → Column families (har row ke liye same; lekin sabhi families fill karna zaroori nahi) → column qualifiers (byte[], pehle declare karna zaroori nahi, different rows mein different ho sakte hain; family:column, e.g. personaldata:Name).
  • Cell = row key + column family + qualifier, jisme value aur timestamp hota hai. Values versioned hoti hain (default timestamp; specify na ho toh latest return; default 3 versions per column family).
  • Full KeyValue = (row key, family, qualifier, timestamp) → value. Column families separate files (HFiles) mein stored hoti hain aur separately read ki ja sakti hain.

Storage hierarchy

HFile: (key, value) ke data blocks + metadata, file info, indices aur trailer contain karta hai; har key mein key/value/row lengths, row, family, qualifier, timestamp aur key type hote hain.

Strong consistency: Write-Ahead LogWrite pehle HLog mein jaata hai, phir MemStore mein (log before memory). RegionServer fail ho jaaye toh recovery/boot-up ke waqt HLog replay karke timestamps use karte hue MemStore edits rebuild kiye ja sakte hain.
  • Cross-datacenter replication: ek master cluster, aur other slave clusters tables replicate karte hain; master HLogs slaves ko send karta hai; coordination ZooKeeper ke through hoti hai (/hbase/replication/state, /peers, /rs).
  • Auto-sharding: region scalability ki unit hai: sorted contiguous rows RegionServers ke across spread hote hain, load balancing/failover ke liye move hote hain, aur data grow hone par automatically ya manually split kiye ja sakte hain. Capacity nodes vs regions per node par depend karti hai.
  • Bloom filter: HFile persist hone par generate hota hai, uske end mein store aur memory mein load hota hai; row + column level check karta hai; complete store files skip kar sakta hai (grouped data aur many misses ke liye useful). Example: "row-R" ke liye block index 6 files kehta hai (6 blocks load), Bloom filter sirf 2 ke liye "Maybe" kehta hai (sirf 2 load).
  • Fold, Store, Shift: physical layout logical layout se different hota hai; har value full coordinates (row, family, qualifier, timestamp) ke saath stored hoti hai, columns "row per column" mein fold hote hain; NULLs ki koi storage cost nahi; versions extra rows hote hain.

2Streaming Fundamentals

Batch processingStream processing
DataAt rest (stored)In motion, real/near-real-time
StyleRequest-based bulk, short-livedEvent ya micro-batch driven, continuous, long-lived
AnalyticsRetrospective, reactive, on-demandProspective, proactive, predictive (next best action)

Stream + batch = all-data analytics (historical past + real-time now). Streaming = data ko steady continuous stream mein transfer karna (YouTube, Facebook, Twitter, Netflix…). Applications: fraud detection, sensor anomalies, website monitoring, ad monetization, social trends, intrusion detection. Requirements: 100s nodes tak scale, second-scale latency, simple programming model, batch/interactive integration aur stateful computation mein efficient fault tolerance.

Problems of existing approaches

  • Two stacks (same data ke liye batch + streaming): Hadoop/MapReduce (TBs, high latency) ya Storm (100s MB/s, low latency), dono saath nahi → different programming models, double implementation aur operational effort.
  • Traditional stateful model: mutable state wale nodes ki pipeline; node fail hone par state lost – fault tolerance mushkil.
  • Storm: unprocessed records replay karta hai → at-least-once, isliye state twice update ho sakti hai aur lost bhi. Trident: transactions exactly-once dete hain, lekin external DB mein per-state transactions slow hote hain.
Traditional analyticsNext-generation analytics
Structured, repeatable; data store karne ke liye structure; hypothesis se shuru, selected data test, landing ke baad analysisIterative, exploratory; data hi structure hai; correlations ke liye all data explore; motion mein analysis

3Spark Streaming

Spark ko scalable, fault-tolerant, second-latency stream processing ke liye extend karta hai, with simple batch-like API. Kafka, Flume, Twitter, ZeroMQ, Kinesis, TCP sockets, HDFS se data leta hai; results HDFS, databases aur dashboards mein bhejta hai. (Spark 2.x mein Dataset-based Structured Streaming add hua.) Yeh Spark ecosystem ka part hai: Spark SQL, Streaming, MLlib, GraphX, SparkR, all over Spark Core.

Core idea – micro-batchingStreaming computation ko very small, deterministic batch jobs ki series ke form mein run karo: live stream ko X seconds ke batches mein divide karo; har batch RDD hota hai aur RDD operations se process hota hai; results batches mein return hote hain. Batch size ~1 second ho sakta hai, latency ≈ 1 second; batch aur stream code same system mein rehte hain.

Driver user code run karta hai aur YARN/Mesos/Standalone par executors launch karta hai. Har batch ek graph hota hai jo multiple jobs banta hai; blocks parallelism dete hain. DStream = RDDs ka sequence (RDD@time1 = 0–1 ka data, RDD@time2 = 1–2 ka data, …), jo memory mein held hota hai (immutable, distributed). Workflow: streaming sources (Kafka, Flume, Akka…) + static sources (HBase, MySQL, Cassandra…) → Spark Streaming → MLlib/Spark SQL → storage (HBase, Cassandra, MemSQL, Kafka, Elasticsearch, HDFS).

val context = new StreamingContext(new SparkConf(), Seconds(1))
val lines = KafkaUtils.createStream(context, ...)
val words = lines.flatMap(_.split(" "))
val wordCounts = words.map(x => (x,1)).reduceByKey(_ + _)
wordCounts.print()
context.start()
context.awaitTermination()

  • Power: online machine learning, live aur historical data combine karna, CEP-style window operations.

5Fault Tolerance & Performance

  • RDDs lineage remember karte hain; input batches multiple workers par memory mein replicated hote hain (default factor 2); lost partitions other workers par recompute hote hain; transformations exactly-once hoti hain.
  • Checkpointing: ~5–10 batches ke baad HDFS par state save ki ja sakti hai; StreamingContext mein checkpoint directory chahiye; driver fail ho toh another node par restart karna padta hai.
  • Backpressure: spark.streaming.backpressure.enabled, spark.streaming.receiver.maxRate.

6Sliding Window Analytics

Window parametersWindow length = window ki duration; sliding interval = window operation kitni frequently run hoti hai. Dono batch interval ke multiples hone chahiye. Window ek naya DStream banata hai jiska batch size larger hota hai.

Spark window functions (DataFrames/SQL, Spark 1.4 se) window of rows ke across har row ke liye ek result compute karte hain – aggregates se alag (ek group ke liye ek result) aur UDFs se alag (sirf current row se ek result). Window specification: partitionBy (grouping; ek group ka data ek machine par), orderBy (group ke andar ordering), frame (current row ke relative boundaries).

8Apache Kafka

DefinitionKafka ek open-source, high-performance, real-time messaging system hai: distributed, partitioned, fault-tolerant, scalable; millions of messages/s ko many receivers tak deliver kar sakta hai. LinkedIn mein develop hua, early 2011 mein open-source hua, October 2012 mein Apache top-level project bana (0.8.2.1, May 2015).

Streaming platform (Unix-pipe analogy): Kafka Core = distributed durable pipes (event streams transport/store); Kafka Connect = I/O redirection (other systems ke saath import/export); Kafka Streams = commands ki tarah, streams ko live process karne wali Java library.

Use cases: messaging; real-time stream processing (e.g. Storm ko data dena); log aggregation (HDFS); distributed systems ke liye commit log; event sourcing (time-ordered events); user activity aggregation (portal clicks/searches → real-time monitoring + Hadoop offline analysis). Thousands of companies Kafka use karti hain.

Data model & architecture

ConceptMeaning
MessageInformation ki unit (log line, stock row, error).
TopicMessages ki category; partitions mein split hoti hai.
PartitionOrdered commit log; har message ka offset; ek end par append, doosre se consume; parallelism ki unit; ideally ek server par fit; partition count parallelism set karta hai.
ProducerTopic mein messages publish karta hai; partition decide karta hai.
Consumer / groupTopics read karta hai; consumer group ka member; groups messaging model control karte hain.
BrokerMessages handle karne wala Kafka process (usually ek machine par ek); cluster brokers ka set, ZooKeeper se coordinate karta hai; har partition ka leader delivery aur persistence handle karta hai.

Partition distribution: partitions servers ke across replicate hote hain; ek leader reads/writes control karta hai aur followers replicate karte hain; leader fail ho toh follower leader banta hai; ZooKeeper leader select karta hai.

Queue systemHar message ek consumer group ke sirf one consumer se consume hota hai. E.g. consumers 1, 2, 3 ko messages (1,4), (2,5), (3,6) milte hain.
Publish-subscribeHar message all subscribers ko jaata hai (har subscriber apne consumer group mein); sab subscribers 1–6 order mein receive karte hain.
  • Guarantees: producer se topic-partition tak messages order mein append hote hain; consumers produced order mein dekhte hain; replication factor N, N−1 server failures tolerate karta hai.
  • Replication: primary-backup model; leader writes propagate karta hai aur replicas ka wait karta hai; down replica ko return hone tak skip karta hai.
  • Persistence: Linux file system aur OS page cache use karta hai; data immediately file mein write hota hai; messages compressible message sets mein group hote hain; producers, brokers, consumers same standard binary format use karte hain.

9Quick Revision

Must remember
  • HBase = HDFS par BigTable clone; availability se zyada consistency prefer; region = scalability unit; write order HLog → MemStore → HFile; Bloom filters files skip karte hain; default 3 versions.
  • Spark Streaming = RDDs ke micro-batches (DStream); latency ≈ seconds; batch + stream unified stack.
  • Fault tolerance: lineage + in-memory replication (factor 2) + checkpointing; transformations exactly-once; Storm at-least-once.
  • Window = window length + sliding interval (dono batch interval ke multiples); incremental windows ko inverse function chahiye.
  • Window functions: partitionBy, orderBy, frame; moving average, cumulative sum, lag, rank.
  • Kafka: topics → partitions (offsets, parallelism); producers, consumer groups, brokers; ZooKeeper ke through leader/follower; replication N, N−1 failures tolerate; queue vs publish-subscribe.
